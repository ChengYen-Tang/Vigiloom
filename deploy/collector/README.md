# Collector configuration example

`isolated-sources.example.yaml` is an example for OpenTelemetry Collector Contrib **0.164.0**, not an automatic installer. It defines two isolated trust scopes in one Collector process. For another Collector version, review its release notes and validate the configuration and end-to-end delivery before deploying it. Collector Contrib is distributed under the [Apache License 2.0](https://github.com/open-telemetry/opentelemetry-collector-releases/blob/main/LICENSE).

## Prepare the two sources

In Vigiloom, sign in as an Administrator and create one source credential for each scope and a third dedicated source for Collector self-monitoring on **待加入服務**. Save each credential when it is shown. Configure the corresponding secrets and endpoint through the deployment platform's protected secret/configuration mechanism:

| Setting | Purpose |
| --- | --- |
| `VIGILOOM_SOURCE_A_TOKEN`, `VIGILOOM_SOURCE_B_TOKEN` | The two distinct Vigiloom source credentials used by the Collector exporters. |
| `VIGILOOM_INGRESS_A_TOKEN`, `VIGILOOM_INGRESS_B_TOKEN` | Two independently generated bearer tokens used by applications to authenticate to their respective Collector ingress. These are not Vigiloom source credentials. |
| `VIGILOOM_OTLP_ENDPOINT` | The HTTPS address of the Vigiloom platform followed by `/api/v1/otlp`, reachable from the Collector. The exporter appends the signal-specific path. |
| `VIGILOOM_COLLECTOR_MONITOR_TOKEN` | A third, dedicated Vigiloom source credential for the Collector's own metrics. Never give it to applications or use it in the A/B ingress pipelines. |
| `VIGILOOM_COLLECTOR_METRICS_ENDPOINT` | The platform HTTPS address followed by `/api/v1/otlp/v1/metrics`; the internal metrics exporter uses this full signal-specific URL. |

The example expects `/etc/vigiloom/tls/collector.crt` and `collector.key` for its HTTPS/gRPC listeners, and `/etc/vigiloom/tls/platform-ca.crt` to validate the Vigiloom server certificate. Supply a trusted certificate whose name matches the address used by applications, restrict access to its private key and the secrets, and expose only the ports required by trusted networks. Environment variables can be visible to privileged process or container administrators; use the deployment platform's controls and avoid command-line secret values, logs and screenshots.

Scope A listens on 4317 for OTLP/gRPC and 4318 for OTLP/HTTP; scope B listens on 4327 and 4328. Configure each application to trust the Collector certificate and use only its own scope's ingress token and port. The application must provide `service.name` and `deployment.environment.name`. Services reported by each authenticated source appear on the Vigiloom candidate page; an Administrator approves them before their data is retained. Collector liveness, successful forwarding and application health are separate observations.

The example explicitly sets each Collector HTTP ingress request-body limit to 4 MiB and each gRPC ingress message limit to 4 MiB. These are Collector ingress limits, distinct from the central receiver's 4 MiB encoded and decoded request limits. The 256 MiB memory limiter is a pressure control, not a hard process-memory or request-parser limit. Batching is limited by item count, not encoded bytes: multiple acceptable ingress requests can still form an export exceeding the central limit. Tune application batches and Collector processing to remain within both limits, and validate the chosen deployment under its actual payload sizes.

The example has fixed A/B listeners, authentication and exporters. Add a separate receiver, ingress authenticator, central authenticator, exporter and signal pipelines for each additional mutually untrusted scope. Never permit an application to choose a central source credential. Each Vigiloom source credential authorizes its holder to report data for every service approved under that source, so mutually untrusted applications must not share a scope.

## Application SDK starting settings

[`application.env.example`](application.env.example) provides starting environment variables for an application already instrumented with an OpenTelemetry SDK or compatible auto-instrumentation. It sets a 60-second metric export interval and parent-based tracing with a 10% root sampling probability. The `Logging__LogLevel__Default` entry is an ASP.NET Core configuration setting for application logs at Information or higher; it is not a universal OpenTelemetry setting. Apply the equivalent application logging filter in other languages or frameworks. `OTEL_LOG_LEVEL` controls the SDK's own diagnostic logger and does **not** filter application logs.

Set the application name, environment and its scope's reachable HTTPS Collector endpoint. Provide `OTEL_EXPORTER_OTLP_HEADERS` separately via a protected secret (for example, an `Authorization` bearer header containing that scope's **ingress** token, encoded as required by the SDK). Do not use the Vigiloom central source credential as an application token. Supply the Collector's trusted CA using the application's supported TLS configuration; do not disable certificate validation. If instance-level observations are desired, configure a unique, stable `service.instance.id` for each running instance using that SDK's resource configuration.

Environment-variable support, exporter setup, resource configuration and filter behavior vary by SDK and instrumentation. Some applications set these values in code and may override environment variables. Check and verify the chosen SDK rather than assuming the file instruments an application by itself. Parent-based sampling respects an upstream sampling decision, and unsampled traces cannot be reconstructed by Collector. The application-specific guided .NET integration belongs to REQ-25. See the [OpenTelemetry SDK environment-variable specification](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/) for the standard variable names.

## Delivery limits and operations

The example uses an in-memory batch processor, disables the exporter sending queue, and limits a batch to 100 items. The Collector can acknowledge an upstream request before the batch is persisted by Vigiloom. Process termination or a prolonged downstream failure can therefore lose buffered data. A lost response after a central commit can also cause duplicates. This setup does not guarantee durable or exactly-once delivery; configure and validate a different delivery strategy if that is required. Keep the batch maximum compatible with the effective central quota burst, and verify behavior again after quota changes.

The Collector emits its own metrics every 30 seconds as service `vigiloom-collector` in environment `monitoring`. Approve that candidate under the dedicated monitoring source before the platform retains them. Use the **管線接入** page to see when approved services last stored each signal; follow **查看 Collector 自身回報** to select the dedicated monitoring service and see uptime report times per instance. No timestamp means that the relevant retained data was not found; it does not prove that the Collector or application is offline. Overall Collector health remains unknown until a fuller health projection is available. A Collector liveness probe alone does not prove that every pipeline can deliver to Vigiloom.

After verifying that the selected service uses the dedicated monitoring credential, register the Collector on that page. In **管理來源對應**, associate each business source with the exact exporter identifier in its Collector configuration (for the sample, `otlp_http/source-a` or `otlp_http/source-b`). This mapping is an administrator-maintained observation aid: it does not configure the Collector or grant source credentials. From an instance's **來源轉送** link, select a mapped source to see its retained per-signal counts and recent failure observations. Counts are cumulative and remain separate by telemetry dimensions; they are not proof of delivery or loss.

The comparison uses a single unambiguous cumulative failure series for one exporter, instance and signal. It requires two different measurement times in the same nonzero counter period, a current sample received and measured within 90 seconds, a gap of at most five minutes, and complete observations within the bounded seven-minute query window. Missing or conflicting samples, multiple dimensions, a reset, unsupported values, revoked sources or truncated query results make the comparison unknown. An increase indicates exporter send failures during that interval, which can include attempts later retried; it is not a count of permanently lost data. The 90-second freshness threshold is specific to the example's 30-second telemetry interval; if the interval differs, this display can become unknown or stale before the Collector itself has failed. Reference: [Collector internal telemetry](https://opentelemetry.io/docs/collector/internal-telemetry/).

To rotate a source credential, use the Vigiloom source management page, save the replacement, update the Collector's protected secret, then restart the Collector. The old credential stops working when rotation commits, so expect a delivery interruption until the replacement is active. If the replacement is lost, explicitly rotate again. Never log or share a source credential with application clients.

For an upgrade, keep the previous image and configuration, verify the new version's configuration and authentication in a test environment, then schedule a controlled restart. If validation fails, restore the previous compatible image and configuration and verify reception again. Restarting loses any in-memory batches, so coordinate with application owners and account for the stated delivery limits. Do not downgrade past a database or receiver compatibility boundary without following the platform's migration procedure.
