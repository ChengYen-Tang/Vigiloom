# Agent inbox retention: implementation contract

Status: proposed for REQ-39; this is not evidence that cleanup or configurable replay policy has been delivered.

## Safety invariants

- A receipt is checked before age, clock and capacity validation. While retained, matching original bytes receive the existing acknowledgement and different bytes with the same identity remain a conflict.
- A receipt may be removed only after the configured receipt-retention duration, and only after all replay windows applicable to the receipt have expired. A duplicate must not extend its retention deadline. Disabled or grace rollout states do not permit cleanup.
- Agent enqueue timestamps are not proof of creation time. Keep future-dated legacy receipts until both their retention obligation and the applicable acceptance window plus clock-skew allowance end. Policy decisions use SQL UTC, not individual host clocks.
- Existing receipt timestamps came from an application clock. For pre-upgrade rows, use a conservative trusted start no earlier than the time the upgraded receiver and cleanup policy were activated, and keep such rows for at least the full promised retention after that point. New rows must record a trusted SQL decision timestamp without changing the original timestamp used by existing diagnostics.
- Serialize each Agent cleanup transaction with its receiver using the existing device application lock before taking the policy lock, preserving lock ordering. Atomically delete bounded eligible receipts and advance durable per-Agent cleanup/replay fences; never rely on an in-memory checkpoint. Rollback must preserve both receipt and fence.
- Persist a separate rejection fence for the cleaned enqueue-time region. The existing SQL-clock floor prevents acceptance when time moves backward; it does not by itself prevent a later policy extension from reopening a cleaned interval. Once cleanup has occurred, transitions and future configuration must not re-enable acceptance of that interval. Existing receipts are still checked first.
- A shorter replay window or receipt retention cannot retroactively shorten previous generations' promises. Store enough generation/deadline information to preserve the maximum still-effective obligation. A longer window must not reopen a cleaned interval; the API and UI must describe this limitation before confirmation.
- Run only after every old receiver has stopped and in-flight transactions have drained. Do not allow older receivers to rejoin after cutover: an old receiver can ignore the fence. The administrator confirmation is an assertion, not automatic node detection or process control. A database restore can roll the fence back; REQ-40 owns restore fencing and this work must not claim to solve that case.
- Delete receipt metadata only. Runtime observations and their MessageId deduplication have their own lifecycle and must not be deleted as a side effect. Keep the last-committed-batch diagnostic meaningful when receipt rows age out.

## Execution and verification

- Administrators need a bounded, validated retention configuration with preview, confirmation, concurrency control and audit. Changes must not erase old obligations. Retention starts at seven days; the replay window starts at 24 hours with five minutes of future skew.
- Use the existing Worker and Hangfire scheduling, bounded batches and persistent progress; do not hold locks across multiple Agents or over an entire cleanup cycle. Keep retry and failure information available in the existing administrator jobs view.
- Test real receipt and resend through the existing receiver, including lost acknowledgements, exact expiry boundaries, legacy/future timestamps, concurrent receive and cleanup, SQL clock rollback, generation changes, failure/rollback and resume. Verify SQL constraints, indexes and migrations with an isolated real SQL database.
- The current per-Agent receipt count and byte caps can cause backpressure well before seven days under sustained throughput. Do not call seven-day retention a delivery guarantee or claim 500-Agent capacity without measurements. Any change to those limits must retain bounded resource use and account for database storage and query cost.

## Cutover and policy generations

- Persist a separate cleanup-protocol cutover time from SQL UTC only after all older receivers have stopped and their transactions have drained. It is distinct from replay-policy activation, is not reset by restart or redeployment, and is not inferred from a host timestamp. Pre-cutover receipts are retained until at least cutover plus the full retention duration promised by their applicable policy; if obligations cannot be established, fail closed and keep the receipt.
- Persist central policy generation history and its transition deadlines. On a shorter replay window, retain the prior acceptance allowance through a centrally recorded grace period long enough for outstanding batches under the previous generation; this includes batches not yet received and therefore without receipts. Evaluate a new batch against all still-applicable central generations, not an Agent-declared generation. Enqueue timestamps remain untrusted and do not establish creation time or entitlement beyond the server's documented transition rule. Preserve prior retention obligations for receipts independently of the current setting.
- The durable per-Agent enqueue fence is an exclusive lower bound: after checking a retained receipt first, reject an unseen batch with `EnqueuedAt < fence`. The fence may advance only to a SQL-time boundary for which every applicable replay generation and grace promise has expired; never infer it from the maximum timestamp in a deleted batch. Rows at the boundary remain protected until the predicate is strictly satisfied. The transaction that advances it also deletes only rows whose enqueue times are strictly below that safe boundary and whose individual retention obligations have ended.

For an administrative shortening committed at SQL time `T`, the previous window `W_old` remains eligible for unseen batches until `T + W_old + S`, where `S` is the previously permitted positive clock skew (initially five minutes). At SQL time less than or equal to that deadline, include that previous generation in the union; remove it only when SQL time is strictly later. Always include the current generation and every other still-live previous generation. This is a conservative timestamp-based allowance, not proof that a producer actually queued the bytes before the change. Retention changes preserve a fixed deadline for each existing receipt rather than recomputing a shorter deadline from the current setting. Multiple changes retain each still-live obligation. All additions and comparisons must validate bounds and explicitly test equality, just before and just after the deadline.

Policy mutations and generation insertion or pruning must first take an exclusive SQL lock on the shared policy row for the transaction. The receiver holds that row with `HOLDLOCK` while checking policy and generations; an update lock alone is compatible with readers and does not serialize changes to the generation collection. Do not enable configuration until controlled tests prove this ordering under both read-committed and read-committed snapshot modes.
