# Agent process, OS service, and endpoint observations

REQ-28 records three independent, authenticated Agent snapshot sources. OS services are not logical application services. TCP entries are local listeners; UDP entries are local bound endpoints. An endpoint does not prove external reachability or application health.

The platform compares complete snapshots and reports observed additions, modifications, and removals. These are differences between observations, not a complete process, service, or network event stream; short-lived activity can occur entirely between scans. The process sampling interval also controls these snapshot passes. Passes and other inventory collections share the cooperative CPU, memory, I/O, and durable queue budgets; load, offline transport, and another active pass can delay them.

Process identity is scoped to its Agent. Windows uses PID and process creation time. Linux uses boot ID, PID, and the kernel's original process start ticks; its displayed UTC time is an estimate and is not used to infer a change to the same identity. A parent PID and a listener owner PID are observations, not a verified cross-snapshot process-instance link. Missing permission, an unavailable service manager, missing `ss`, truncation, and inaccessible processes must not be reported as a complete empty result.

Windows queries the service control manager and the local IP Helper owner tables; account identity is the process primary token's SID where readable. Linux queries systemd where available, local processes via procfs, and `ss` for TCP listeners and UDP bound endpoints; the effective UID is reported where readable. Linux distributions without systemd or `ss` may expose fewer capabilities. The managed network fallback can list endpoints but cannot identify their owners and is reported as partial. These observations do not assert support for an untested OS, architecture, service manager, or privilege configuration.

A partial observation is retained separately from the last complete snapshot. It can be queried with its own snapshot ID, but it never replaces the complete baseline or creates removal events. Two observations can yield `NewlyObserved` or `ObservedModified` records: these describe what became visible or changed between incomplete views, not proven creation or modification events. A later terminal attempt replaces the prior partial observation. Both complete and retained partial data count toward the per-Agent snapshot storage budget.

Schema 5 can record bounded partial-reason flags for access denial, an unavailable tool, an unavailable endpoint owner, truncation, and other incomplete reads. Multiple reasons can occur together; an unavailable owner does not itself prove access was denied. The reasons contain no exception text, command output, or paths. Earlier snapshots without a reason remain readable. Downgrading the database across the reason-column migration is rejected while stored reasons exist, so that a later upgrade cannot silently lose manifest information.

Executable-path collection is disabled by default and can be set at platform or device scope. When enabled, the Agent reads the executable path only; it does not read command arguments or environment variables. The displayed command representation consists of that path and a fixed masked-arguments marker. Settings propagate on the normal Agent configuration schedule. Turning collection off prevents later scans from reading paths after the policy is applied; snapshots and change history already stored remain subject to retention policy. All such data remains behind authenticated monitoring authorization and is excluded from public projections.

Inventory wire schema 4, its canonical digest, and its legacy status response remain compatible with previously deployed Agents. New sources use schema 5 and an explicitly negotiated status response. A legacy Agent receives a retryable response while an incompatible source is staging, rather than an incomplete view of the shared producer fence. Version-5 queued or retained batches hold a stronger local queue version fence so an older Agent does not interpret them. The settings store writes a version-1 compatible mirror for Agent rollback; a separately stored extended policy applies only when its owner and save token match the mirror.
