# Speed-test retention

Speed-test results default to 365 days; an Administrator can set 1–3650 days. The policy uses `RequestedAt` in UTC, matching the history query. It is distinct from Ping and application-health retention. Changes use the existing speed-setting rowversion and a typed audit event. Before a reduction, the settings page shows an impact estimate and requires a confirmation bound to the administrator, proposed days, rowversion and a five-minute database-clock window. Changes to the setting or cleanup progress invalidate an older confirmation. Extending retention cannot restore deleted data. Multiple Web nodes require the existing shared Data Protection key ring and application name.

The Worker registers an hourly Hangfire job. Each run executes at most ten independent transactions of at most 500 rows. Each transaction locks the existing speed-setting row, reads the database UTC clock and current retention policy, then deletes the oldest terminal results whose `RequestedAt` is strictly before the cutoff. Queued and running work is excluded; work started or requested within the last 24 hours is protected because the existing schedule and usage view rely on that window. Rows beyond the policy can remain queryable until cleanup catches up. The history page reports both the configured days and the earliest actual stored result.

Each committed batch updates cumulative deleted count and the most recent batch count/time in the same transaction as the deletion. A failed or cancelled later batch leaves earlier progress intact and Hangfire records the failure; retry or the next scheduled execution continues from remaining rows. Cleanup rechecks the latest policy before every batch. The existing `(RequestedAt, RowId)` index supports selection; the batch bound limits transaction size but is not a measured performance guarantee.

Deleting a result also removes its request identifier. Speed test jobs create a new request identifier for each invocation; this design does not promise permanent request-id deduplication after retention. No other data source is cleaned by this job. Ping, telemetry, audit, alert and intelligence retention remain part of REQ-39 and must respect their own prerequisites and evidence requirements.
