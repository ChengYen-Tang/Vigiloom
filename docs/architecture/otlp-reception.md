# OTLP reception

Status: implementation in progress. The central receiver supports OTLP/HTTP binary Logs, Metrics and Traces; it does not expose an OTLP/gRPC receiver. An opt-in integration test exercises the supplied isolated-source Collector configuration against the HTTP receiver, including a database outage. Wider deployment and contention validation remain unfinished.

The Docker integration test uses the supplied Collector Contrib 0.164.0 configuration to send Logs, Metrics and Traces over both OTLP/HTTP and OTLP/gRPC to the Collector, then verifies their delivery over OTLP/HTTP to the platform and SQL. It checks the gRPC ingress rejects another scope's token for each signal, and checks selected metric values, trace identifiers, timestamps and instance identity after storage. This test is opt-in and requires Docker and a disposable SQL test database; it does not establish central OTLP/gRPC support, complete protocol-field coverage or delivery guarantees across a Collector restart.

The same test exhausts the shared Log budget and the separate Trace budget, observes retryable central failures through the Collector, then restores capacity and verifies the distinct test logs and spans were retained. It also verifies Log ingress limits for HTTP and gRPC, and rotates a central source credential before restarting the Collector with the replacement and verifying new delivery. The Collector's HTTP oversized-body response in this test is 400, not the central receiver's 413. These examples do not establish durability of in-memory data during restart.

## Protocol boundary

Generate .NET message and gRPC types from the official OpenTelemetry protocol definitions, pinned at `v1.11.1` and included with their Apache-2.0 license. The evaluated `Meziantou.Framework.OpenTelemetryCollector` 3.0.6 contains a reduced LogRecord schema without trace, span, severity and observed timestamp fields; it cannot preserve the required OTLP data and is not used. Request-scoped identity and database transactions must not be stored in singleton handlers. A receiver must never acknowledge an in-memory buffer before durable storage succeeds.

Authenticate the application-source credential at ingress and derive the trusted source ID from the authenticated principal, never from resource attributes. Inside each short database transaction, revalidate the source and service binding with the REQ-22 authorization primitive and use that same transaction for telemetry and quota. A shared Collector must preserve a trusted mapping to the originating source; a self-declared service name is not an authorization credential. For unapproved bindings, only bounded discovery metadata may be persisted, after any authorization transaction ends; no raw payload, queue, or diagnostic log may persist unapproved telemetry.

An application-source credential is a trust boundary, not an individual service identity. Its holder can submit data to every service approved for that source by declaring its name and environment; resource attributes do not prove the emitting application's identity. Applications that must not impersonate each other therefore require separate source scopes and credentials. For a shared Collector, authenticate each application ingress independently and map it to a fixed exporter and corresponding central source credential. Do not allow an application to select an exporter, set the central credential, or choose its trusted source mapping via telemetry attributes or unverified headers. A common Collector process can host these isolated pipelines; the central exporter secrets must not be distributed to application clients. This boundary must be proven with cross-application spoofing tests before claiming secure Collector interoperability.

The identity mapping uses `service.name` and `deployment.environment.name` as the existing logical key and environment, with `service.namespace` as a separate, exact identity field and `service.instance.id` optional. Ambiguous, non-string or invalid identity attributes are rejected; namespace and instance identifiers retain their original text. Missing or empty namespace maps to the legacy identity; adding a namespace creates a separate candidate that requires approval. The source scope remains independent from these attributes. This mapping does not imply that every SDK supplies the attributes by default; onboarding must document how to configure them.

The schema migration and namespace-aware code must be deployed to all Web and receiver nodes before accepting a nonempty namespace. Mixed old and new nodes can otherwise authorize the wrong service because old queries do not include namespace. The existing metadata endpoint currently rejects nonempty namespaces until the deployment boundary and actual receiver are ready; do not expose namespaced ingestion prematurely. Once namespaced data exists, an old binary cannot safely resume service without a compatible rollback plan.

## Resource and response limits

The host must enforce compressed and decompressed byte limits, bounded concurrent requests, structure and field limits, and a separate gRPC receive limit before exposure. The default ASP.NET Core request body limit alone is not evidence that decompressed or gRPC sizes are bounded; tests must exercise each actual transport.

The HTTP binary receiver limits both wire and decompressed bodies to 4 MiB, admits at most four requests concurrently without queuing, and checks a maximum nesting depth of 32 and 100,000 protobuf fields or packed values before allocating the message graph. The concurrency guard precedes authentication; a 30-second cooperative deadline covers the whole request. Unknown length-delimited fields are preserved; protobuf groups are rejected. The receiver applies further bounds of 256 groups and 10,000 records, spans or metric points after parsing. These are reception policies, not a claim that every valid OTLP payload is accepted. A request exceeding them fails before candidate discovery or database writes. The gRPC transport needs its own pre-deserialization resource policy.

Handler success is returned only after committed persistence. For temporary quota, database, or capacity failure, produce the transport's retryable response, including a reasonable retry delay where supported. OTLP partial success is non-retryable; reserve it for permanent, explicitly counted rejection, and never use it to hide a transient write failure. Batch coordinators authorize all service bindings and commit accepted records in one transaction. Standard OTLP does not guarantee exactly once, including when a response is lost after commit.

`LogExport` admits accepted records once and commits the request in one transaction. SQL regression tests cover the prior 60/40-scope starvation case, reversed service order under concurrency, an over-burst batch and a database write failure. An ordinary request exceeding one effective burst needs an explicit delivery strategy: blindly retrying the same request can never succeed.

The coordinators reserve quota once for all accepted records and commit them in one SQL transaction. Before resolving instances they acquire the instance policy and involved service instance locks in a consistent order, then acquire the global instance-admission lock. Quota policy and quota locks follow those locks. Temporarily failed admission, instance resolution or database writes roll back formal records, newly created instances and quota. Discovery uses a different lock order and occurs outside the formal write transaction.

An export larger than the effective burst cannot be atomic and fit that burst. The controlled Collector needs a hard batch maximum (`send_batch_max_size`), matched to the effective quota; exceeding it requires a clear non-success outcome rather than endless retries. Configuration changes and broader interoperability scenarios still require end-to-end validation.

## Retained data queries

Authenticated Administrator, Read only and `monitoring.read` API clients may use `GET /api/v1/service-telemetry/{serviceId}/logs`, `/traces`, or `/metrics`. These responses may contain sensitive application telemetry and must not be exposed through anonymous publication. The required `from` and `to` parameters use UTC, with an inclusive start, exclusive end, maximum 31-day range, and 1-based `page` from 1 to 100. Each page holds at most 25 items; `hasMore` indicates a subsequent page within the bounded window. If more records exist beyond page 100, `truncated` is true and the caller must narrow the time range. Logs and traces may filter by nonzero 16-byte `traceId` encoded as 32 hexadecimal characters.

Binary fields in the JSON response are base64 protobuf messages from the pinned OTLP definitions. Each item's zero-based `context` is an index into the response's `contexts` array, not a database identifier. Shared context contains the original OTLP `Resource` and `InstrumentationScope` and their schema URLs. Log `record` and trace `span` are the original OTLP messages. For metrics, context `metric` is the original `Metric` metadata with data points removed; `point` holds the original point message. `kind` 1 or 2 means `NumberDataPoint` (gauge or sum), 3 means `HistogramDataPoint`, 4 means `ExponentialHistogramDataPoint`, and 5 means `SummaryDataPoint`. Trace and span identifiers are returned as lowercase hexadecimal without Guid conversion. `usedReceivedTime` and `usedObservedTime` distinguish a log timestamp fallback. Raw context and payload can contain application secrets; they must never enter public projections or routine diagnostic logs.

New metric contexts carry an optional exact-name lookup key for names up to 256 UTF-16 code units; longer names remain available in the original protobuf. Historical contexts created before this lookup was added are not backfilled. A lookup miss therefore does not establish that a metric was never received. The index's storage and write costs have not been benchmarked.

Trace admission uses a separate central bucket and per-authenticated-source/service buckets. Initial rates are 2,000 spans/s with burst 4,000 centrally and 200 spans/s with burst 1,000 per service source. Administrators can change these through the Trace quota settings and changes are audited. Admission is one call for the whole accepted request, in the same transaction as the writes. Broader concurrent failure tests remain unfinished.

## Collector self-monitoring

The pinned two-source example exports the Collector's internal metrics directly to the platform every 30 seconds using a third, dedicated source credential and a distinct `vigiloom-collector` / `monitoring` service. The Collector integration test verifies that its uptime metric reaches approved, durable storage. The monitoring credential must not be shared with applications or used for business ingress. Source authorization, not resource names or metric attributes, defines the trust boundary. The management UI lets an Administrator register a Collector, manage explicit source-to-exporter associations and inspect per-instance uptime report times. Associations are descriptive and do not modify the Collector or grant ingestion rights. Pipeline interpretation is not yet available, so overall health remains unknown.

Administrators can inspect a selected monitoring service's recent uptime reports at `GET /api/v1/service-reception/collector-observations/{serviceId}`. The endpoint returns at most 50 instances per page, a database-clock cutoff and only data received during the preceding 24 hours. It reports unidentified instances separately, includes source revocation, service stop and instance retirement timestamps, and does not infer an overall healthy state. The administrator must independently verify that the selected service's credential is dedicated to Collector telemetry; a matching metric or service name alone does not prove origin. A missing report can mean no data, cleanup, pre-index historical data, transport failure or another interruption.

The pinned Collector's `health_check` extension provides liveness/readiness, but its `check_collector_pipeline` option is documented as unreliable and must not be used to claim pipeline health. Internal exporter failure and sent counters can support future diagnostics, but they require correct instance, metric, temporality, attribute and measurement-time matching. In the real Collector test, a temporary database failure followed by successful retry did not produce an exporter send-failed metric in the observed export. Absence of that metric must not be interpreted as zero failures. Counter resets and missing samples must remain unknown rather than becoming false healthy results.

## Source credential rotation and upgrades

An administrator can replace a source credential in the service discovery page. The replacement preserves the source and its approved services, and the old credential stops authorizing transactions once rotation commits. Copy the new secret immediately and update the corresponding Collector; it is not displayed again. If the response is lost, check the source and explicitly rotate again to obtain a usable secret. Concurrent rotations using an older page are rejected.

Before applying the source-version migration or enabling rotation, stop and drain **all** old Web receivers, apply the migrations, and start only upgraded receivers. Older nodes cannot enforce the authenticated credential version and must not run alongside the upgraded nodes. This follows the coordinated migration procedure in `sql-server-migrations.md`.

## Bounded rejection diagnostics

The Administrator reception page exposes three fixed counters: rejected credentials, a previously authenticated source becoming unavailable, and requests containing an unapproved or stopped service. The last category includes normal discovery before approval and must not be interpreted as confirmed impersonation or an attack. Invalid timestamps and malformed data do not count as service-authorization failures. Each category keeps an ingress and, only where authentication succeeded, one representative source from the most recently persisted aggregate. The total combines all sources; the sample is not a per-source total or a complete event history. An unauthenticated bearer value is never used to infer a source identity.

Each Web process accumulates fixed-size counters in memory and flushes them to three fixed SQL rows every 30 seconds. A process restart before flushing, database failure, cancellation, or an uncertain commit can lose some observations. A timed-out delta is not replayed because its commit outcome may be unknown. SQL timestamps are persistence times, not the exact rejection time; across nodes, the sample is from the last completed flush rather than the globally last request. This diagnostic does not replace the transactional audit records for administrator approval, stopping collection or revoking credentials, nor does it guarantee a complete security-event history. Tokens, request bodies, IP addresses, caller-supplied service names and exception messages are never saved in these summaries.
