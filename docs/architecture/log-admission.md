# Shared log admission

REQ-23-T03 owns the single admission policy for both host and application log records. Agent and OTLP reception remain responsible for authenticating their own producer, validating bounded batches and handling protocol-specific replies; neither may select a quota key from an unauthenticated field. The policy counts records rather than HTTP requests. Initial limits are 20 records/second and burst 100 per trusted source, and 1,000 records/second and burst 2,000 centrally. Administrators can change these values; they are policy defaults, not a throughput claim.

All central Web/Worker instances must share the same counters. .NET's in-process partitioned token buckets do not provide a single limit across processes. The SQL Server provider in `DistributedRateLimiter` supports a shared token bucket, but its public `CheckAsync` accepts one key and one permit per call, and does not accept a caller-owned transaction. It therefore does not provide atomic, weighted admission against both the central and source buckets as required here. Introducing Redis solely for this feature would add a new required deployment dependency. Use the existing SQL Server for shared state, and reassess a maintained package if its public contract satisfies these requirements.

The receiver opens a short SQL transaction after authentication and bounded parsing. Lock order is business authorization and deduplication, quota policy, global bucket, source bucket, then data writes. Agent batches already committed must return their prior acknowledgement before quota admission. The receiver admits the exact number of new log records against both buckets, writes the accepted records and commits before acknowledging success. A failed or rolled-back write cannot permanently consume quota or acknowledge data. A rejected batch does not debit either bucket. Errors, cancellation and database unavailability fail closed; the protocol adapter maps temporary capacity exhaustion to an appropriate retryable response and does not claim successful persistence.

Bucket state uses the database UTC clock, not caller clocks. Time moving backwards never adds tokens or moves the stored refill time backwards. Policy changes have one effective central version; every caller sees the same persisted configuration. On a policy revision, preserve existing tokens up to the new burst, discard unaccounted refill before the policy's effective time, and apply the new rate only from that effective time; never refill the old interval at the new rate or reset the bucket to full. This calculation also works when a rejected transaction rolls back without persisting the revision. Restarting an application node must not reset budgets. The implementation must explicitly bound source keys and cleanup safely; a cleanup cannot silently reset an active bucket. Bucket rows are internal operational state with a bigint clustered key and unique typed source key; the global bucket's empty identifier is an internal sentinel, never a resource ID.

An incoming batch larger than either effective burst can never fit as one atomic admission. The receiver must detect this condition and report a clear non-successful size/policy outcome; an upstream producer needs to split it. This is distinct from a temporarily exhausted bucket, and it must not be retried forever as though time alone could make it fit. OTLP and Agent adapters must document their actual batch and retry semantics.

The global SQL row may become a contention point. Validate actual throughput and latency under realistic multi-source load before claiming support for a particular log volume; the defaults are not performance measurements. The complete integration with real host and application logs is accepted only once REQ-29 and REQ-23 receivers both use this same mechanism.
