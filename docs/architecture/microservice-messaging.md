# Microservice work delivery

Temporal Server, backed by PostgreSQL, coordinates durable work between services. Each destination service runs a worker on its own task queue. Task queues distribute work among workers; delivery to multiple services requires a separate work request per destination.

For a business change requiring reliable delivery, use `TemporalWorkWriter` with the current EF Core SQL Server transaction for each destination; the returned delivery ID identifies that destination’s work. `OutboxDispatcher` retries delivery to Temporal using the message ID as the workflow ID. A receiver can use `TransactionalWorkHandler` to commit its SQL business change and delivery receipt in one transaction. Each participating service must register its own worker and handler, apply the scheduling migrations, and run its dispatcher. These integrations are completed by the owning service requirements.

Use the workflow handle to query its execution status, obtain its result, or request cancellation. Activities retry ordinary failures under Temporal’s retry policy; a handler can report a permanent failure with `ApplicationFailureException` marked non-retryable. Handlers must cooperate with the cancellation token. The workflow waits for the activity cancellation response; a timeout or uncooperative handler cannot guarantee that an external operation has stopped. Workflow state and results are available from Temporal; an accepted request is not proof of a completed operation. Workflows and receiver receipts have distinct retention concerns. Send references to large data rather than the data itself. Replaceable periodic updates need not use durable delivery when their owning service can tolerate loss.

For local development and integration tests, see [Temporal for local development](../../packaging/temporal/README.md). The SQL Server integration fixture remains separate.

The existing shared-database retention job removes completed outbox records according to the administrator's background history retention setting; pending work is retained. When a service moves to its own SQL database, its integration must apply that policy to its own outbox. Receiver receipts are not covered by this cleanup because retries can arrive after the sender has been offline; do not delete them without a compatible delivery and deduplication retention policy. Temporal manages workflow history through namespace retention.

Operations includes the Resources, Network, Observability and Security service databases in its history preview and cleanup when their respective `Services:<name>:Url` settings are configured. Configure these internal URLs for deployed services. Operations counts a shared SQL database once and retains pending dispatches; if a configured service is unavailable, the preview or cleanup fails and can be retried when it returns.
