# Operations database

Create an empty, non-system SQL Server database for the Operations service. Set `VIGILOOM_OPERATIONS_SQL_CONNECTION` to its connection string and run `Vigiloom.Migrator initialize-operations`. To copy existing platform data, set `VIGILOOM_MIGRATION_SQL_CONNECTION` to the existing platform database and run `Vigiloom.Migrator migrate-operations` instead. The command applies the operations, shared Log quota, centralized Log, and scheduling EF Core migrations, initializes Hangfire storage, then copies existing operations records, quota settings, host and application Logs, and LINE delivery work into the empty target. Configure the Operations host's `ConnectionStrings:Operations` with the same connection string.

On Windows, the development host defaults to LocalDB database `Vigiloom_Operations_Development`; create that database and initialize it before starting the host. The `/internal/v1/log-quota` endpoints are for the trusted service network and must not be exposed through the public gateway.

Operations receives `notification.create.v1` and `operation-audit.write.v1` work on the `vigiloom.operations` Temporal queue by default. It also consumes the resource service's existing audit work on `vigiloom.operations.audit`. Set `Temporal:Address` and `Temporal:Namespace` for the deployment; `Work:OperationsQueue` and `Work:AuditQueue` can override the queues. Both services must use the same audit queue name. Records and work receipts commit together, so a retried delivery does not create duplicates. Other monitoring and security services still need to be connected to the Operations queue.

The Operations host registers its hourly history cleanup on the `operations` Hangfire queue. Set `ConnectionStrings:Scheduling` to the Hangfire database shared with the other services; when omitted, Operations uses its own initialized database. Other service workers and the Dashboard must use that same database when deployed together. Operations runs a lightweight Hangfire worker and requires a regular Hangfire Server against the same storage to enqueue recurring jobs; the existing Worker supplies that scheduler during migration. The shared job type is available to that scheduler, while only Operations workers consume the `operations` queue.

`/health/live` reports process liveness; `/health/ready` checks only connectivity to the Operations database. The trusted `/internal/v1/diagnostics/jobs` endpoint combines shared Hangfire statistics with Operations' own outbox counts; it does not represent other services' outboxes.

The internal `/internal/v1/events` endpoint queries timeline summaries and obtains group membership from the Resources service at `Services:Resources:Url` (default `http://vigiloom-resources`). The `event-timeline.append.v1` work type accepts summaries, and newly received host and application Logs create summaries in their storage transaction. Existing histories, other sources, application Log body display, and timeline retention have not yet been connected; do not switch the Web timeline to this endpoint until REQ-50-T06 is complete.

Keep the existing Data Protection keys and application name available to Operations so migrated LINE credentials remain readable. Stop writes to the old platform during migration. Operations can dispatch existing deliveries, group new notifications, and accept LINE configuration and webhooks through its internal API. The Web management interface and gateway have not yet been switched to these endpoints; do not cut over LINE until REQ-50-T02 is complete. The trusted host-monitoring service can submit authenticated Agent Logs to `/internal/v1/host-logs`; the Operations service commits new records, shared quota usage and security work together. The security service consumes the queued references once its REQ-49 integration is available. The trusted observability service can submit approved application Logs to `/internal/v1/application-logs`; both sources use the same global Log quota. Integration with the actual host and observability services remains to be completed.
