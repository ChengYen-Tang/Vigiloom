# SQL Server module migrations

## Security service cutover

For an existing installation, stop the old Web and Worker processes and wait for running security work to finish before copying data. Create an empty target SQL Server database and set `VIGILOOM_MIGRATION_SQL_CONNECTION` to the existing platform database and `VIGILOOM_SECURITY_SQL_CONNECTION` to the target. Run `dotnet run --project src/Hosts/Vigiloom.Migrator --configuration Release -- migrate-security`. For a new installation, set only `VIGILOOM_SECURITY_SQL_CONNECTION` and use `initialize-security`. These commands apply the Security and scheduling migrations; the copy command also transfers retained security data and YARA scans.

Configure Security with `ConnectionStrings:Security`, the shared `ConnectionStrings:Scheduling`, `Temporal:Address`, and its internal `Services:Resources:Url`, `Services:Host:Url`, and `Services:Operations:Url`. Enable `Hangfire:Enabled` on Security for intelligence refresh, reassessment, and expiry jobs. The shared Hangfire storage must also have a normal scheduler running; the Security worker consumes the `security` queue.

Configure the Web, Worker, HostMonitoring, Operations, and Observability processes with `Services:Security:Url`. After the copy and Security service are ready, set `Services:Security:IntelligenceEnabled=true` on Web and Worker to move intelligence management and retire legacy security schedules. Set `Vigiloom:Gateway:SecurityCutover=true` on Gateway to route Agent security requests and batches to Host/Security. Apply these settings together when restarting the services; setting the Security URL alone does not enable every cutover. Agent work already running before the stop must finish or be recovered before the copy.

Use the same existing `Vigiloom:DataProtection:ApplicationName` and key ring for services that need to read protected intelligence credentials. If a certificate protects the key ring, the Security process must also be able to use it. Keep all credentials outside the repository. Operations and Observability use their own retention policies when cleaning Security data through its internal API.

REQ-02-T02 supplies the first production migrations for `identity`, `resources`, and `network`. Each module owns its context, schema, and separate `__EFMigrationsHistory`. Devices and groups belong to Resources; network samples refer to a device GUID through a `NO ACTION` cross-schema foreign key. The Network migration deliberately adds that foreign key without a CLR reference to the Resources module. Future migrations must preserve it and follow the dependency order below.

EF Core 10 SQL generation explicitly targets compatibility level 150. The deployment database must have SQL Server compatibility level 150 or higher; configuring EF does not change the database level. Integration tests set temporary databases to 150 and record the actual SQL engine. SQL Server edition, hosting, and higher compatible levels are deployment choices, not hard-coded editions. Microsoft documentation: [SQL Server provider compatibility](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/#compatibility-level).

## Applying migrations

Supply a SQL Server connection with the permissions needed to create schemas, tables, indexes and foreign keys. Back up and review generated migration scripts before applying them to an existing environment; migrations are a deployment operation and do not run automatically on Web or Worker startup. Keep credentials outside the repository. For local development the design-time factories default to `Vigiloom_Development` on `(localdb)\MSSQLLocalDB`; set `VIGILOOM_DESIGN_SQL_CONNECTION` to override it. The target database must already exist.

```powershell
$env:VIGILOOM_MIGRATION_SQL_CONNECTION = '<connection to the existing target database>'
dotnet run --project src/Hosts/Vigiloom.Migrator --configuration Release
```

The deployment tool applies the modules in dependency order and initializes built-in roles; it may be rerun after a successful deployment. Publish the Migrator project with `dotnet publish` when deploying without the SDK. It refuses system databases and requires the target database to exist. Use a deployment identity with schema-changing permission; Web and Worker need only their normal runtime permissions. For development-time EF commands, install `dotnet-ef` (for example, `dotnet tool install --global dotnet-ef`) and set `VIGILOOM_DESIGN_SQL_CONNECTION` when targeting something other than the LocalDB development database.

For a confirmed new installation on an empty target database, deployment automation can run the same Migrator with the `fresh-install` argument. Before migrations it verifies the database is empty and persists an installation intent; once all steps complete it atomically initializes the Agent replay policy to the 24-hour default and marks the intent complete. If interrupted, rerun `fresh-install` to resume; ordinary migration refuses an incomplete fresh intent. A completed fresh invocation is idempotent. An existing nonempty database without that intent is never accepted as a fresh install. Keep Web and Worker stopped throughout deployment, including recovery, and do not allow old receivers or in-flight transactions to access the database. All current Migrator modes share a deployment lock; if its connection fails, the next stage check aborts, but an operation already running on another connection may finish. Older Migrator binaries do not honor this lock and must be stopped. Ordinary migration is the upgrade path and leaves an existing disabled policy disabled until an Administrator completes staged rollout. Neither command automatically cleans Agent receipts.

Resources must precede Network and AgentManagement because of their device foreign keys. Identity is independent. Generate a reviewable repeatable deployment script for each module with `dotnet ef migrations script --idempotent --project <module-project> --output <path>` and execute scripts in the same order. Dropping or rolling back Resources while Network or AgentManagement references it is intentionally blocked; roll back dependent migrations first. Do not share migration history tables between modules or edit an already deployed migration.

The Identity data layer provides `RoleInitializer.InitializeAsync` for the two built-in roles; the deployment tool invokes it after migrations. The first administrator is created separately through the setup page with the configured setup token. Role initialization uses SQL transaction-scoped application locking, preserves existing role IDs, and allocates retry IDs before the execution strategy starts. It is safe for concurrent hosts and is tested against a real SQL database.

Web and Worker register per-operation context factories; callers must dispose each context, and Worker jobs should create a fresh context for each unit of work. Do not keep a context for a Blazor circuit or share it across concurrent operations. Each application configures `ConnectionStrings:Vigiloom`; development uses the separate LocalDB database. See [database isolation](development-and-test-databases.md) for tests and cleanup.

For model changes, read [ADR-0001](ADR-0001-identifiers-and-keys.md), add the owning module migration using a `dotnet-ef` version compatible with the project's EF Core packages, inspect it for key and cross-schema constraints, test on SQL Server, and check `dotnet ef migrations has-pending-model-changes --project <module-project>`. Cross-module references are `NO ACTION` and must not introduce direct module implementation dependencies. EF snapshots cannot model Network's and AgentManagement's manually declared cross-module FKs: preserve them explicitly in future relevant migrations.
