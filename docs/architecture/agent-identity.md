# Agent registration and identity

REQ-18 owns the Agent's registration, device binding and machine credentials. REQ-19 owns the actual telemetry receiver and durable transport; REQ-20 owns installation and update. This is a design for REQ-18, not a claim that those components have been implemented or verified.

## Identity and enrollment

An Administrator explicitly selects an existing deep-monitoring device and issues a short-lived enrollment secret bound by the server to that device. Issuing a secret does not create a running Agent. The server stores only a verifier for a cryptographically random secret and exposes the secret only at issuance. Enrollment is a TLS-only, rate-limited operation; a caller cannot nominate a different device or use a human/API identity as an Agent identity. The Agent creates and safely persists its own random machine secret before enrollment and sends its verifier with the enrollment secret. The server returns the Agent resource ID after committing the binding. The credential's secret is never generated or returned by the server.

The same unexpired enrollment secret and identical machine verifier may retry an already committed registration to recover a lost response; they return the existing Agent ID and do not create another binding or credential. A different verifier, expired, replaced, revoked or otherwise invalid enrollment is rejected. After expiry, a distinct recovery operation can return an already-created Agent ID only when the caller proves possession of both the enrollment secret and the original machine secret, and the Agent and device are still authorized. Recovery cannot redeem an unused enrollment or create or change credentials. The enrollment secret is an authorization capability, must be handled as sensitive, and cannot be used as a machine credential. Enrollment verifiers and machine verifiers never appear in list responses, logs or user-visible diagnostics. Administrative replacement requires explicit revocation/re-enrollment; unique database constraints and short transactional operations arbitrate parallel attempts.

The machine presents its own bearer credential over TLS using a distinct scheme and prefix. The server derives the Agent and device from its credential store, checks revocation and current device authorization on every request, and grants only Agent-specific permissions. The verifier is a SHA-256 digest of a 256-bit random secret and comparisons use fixed-time comparison. Agent IDs and enrollment IDs are UUID v7 resource identifiers, not authentication. SQL clustered storage keys remain internal. Neither a caller-provided device ID nor a device address proves ownership.

The Agent writes its machine secret and enrollment data to a protected, exclusively leased state directory before sending a registration request. It keeps that pending state across failures and first attempts proof-based recovery if a request was rejected after an earlier response may have been lost. To replace an unregistered pending state, an operator must first revoke the old enrollment and any Agent it created, issue new enrollment data, and explicitly confirm the reset. A registered identity is never silently reset. Enrollment input is read without echo or command-line secret arguments; the installer-owned workflow will provide the final guided experience.

The initial local vault uses Windows user-scoped DPAPI and a restricted, non-inheriting directory ACL. A directory handle that does not share delete access remains open for the session, and existing reparse points in its path are rejected. It must be created and reopened under the actual Agent service identity; changing service accounts requires a managed recovery process. Use a protected parent directory as well: concurrent ancestor replacement by another account has not yet been fully verified. Linux uses a service-account-owned 0700 directory and 0600 files, validates ownership and ancestor permissions with the Linux x64 `statx` ABI, and rejects symlinks or untrusted writable parents (a root-owned sticky parent such as `/tmp` is allowed). Linux file contents are protected by OS permissions, not encrypted by this vault; disk encryption is a deployment choice. The vault fails closed when these checks cannot be made. Writes use a same-directory temporary file, flush its contents and rename it; this does not claim the directory entry is durable across every filesystem or sudden power loss. Update, backup, service-account changes, power-loss recovery, and each supported OS/libc combination require explicit REQ-20 verification.

## Device lifecycle and concurrency

Resources owns device state. A monotonically increasing device Agent authorization generation changes atomically when a device is archived. An issued enrollment and registered Agent are bound to the generation. A mismatch permanently invalidates them even if the device is restored; restoring the device never restores its old credentials. A currently archived, disabled or non-deep-monitoring device cannot authorize Agent operations. Disabling monitoring or switching modes suspends authorization while the setting applies; archive changes the generation and requires new enrollment. Modifying name or address does not change the generation.

The Resources module exposes a narrow device-authorization contract instead of exposing its entities. Enrollment checks and locks the device state in the same short SQL transaction used to create the binding. Consumers that commit Agent-originated data must also revalidate and lock the Agent credential and device generation inside their own commit transaction; a successful earlier authentication alone cannot fence a concurrent archive or revocation. REQ-19 owns that receiver transaction and its tests. This document does not claim cross-module immediate revocation has been verified until those integration cases exist.

## Rotation, storage and recovery

Revocation is centrally effective on the next authorization, including when the Agent is offline. For rotation, the Agent first persists a new random secret locally and uses its existing credential to register the new verifier. Only the existing credential remains valid for normal access; the pending secret can confirm rotation for 15 minutes. Confirmation atomically replaces the old verifier and is idempotent with the committed new credential if its response is lost. A retry of the same start is idempotent; a competing pending verifier is rejected. Expired pending rotation leaves the old credential active. The Agent must retain both secrets until it has confirmed which one is active; its local implementation and crash recovery require REQ-19/20 integration. Operators can revoke an exposed enrollment or machine credential and re-enroll. The Agent's installation/data directory is separate from version directories; access to local secret material is limited to its service identity and administrators as supported by each operating system. Setup, file protection and reinstall/update recovery are implemented and verified together with REQ-20, rather than claiming ordinary configuration files are a cross-platform secure store.

No secret belongs in query strings, logs, job arguments, public projections or read-only monitoring responses. Administrator UI shows a newly issued enrollment secret once and provides explicit expiration, revoke, recovery and lost-secret states. Read-only users cannot issue, rotate or revoke. The UI follows the existing product design and its security checks are enforced again server-side.

## Verification

Use real SQL Server to exercise concurrent redemption, same-request retry, mismatched replay, expiration, device changes, archive/restore, revocation and replacement. HTTP tests must exercise TLS, distinct principal schemes and Administrator authorization; a credential from one principal class cannot access another's routes. Check the physical indexes, constraints and resource identifiers against ADR-0001. Verify Agent local storage, transport and real operating-system installation as their owning requirements become available. Do not mark REQ-18 complete until its cross-requirement acceptance conditions are met.

ASP.NET Core's built-in authentication scheme infrastructure and the existing project credential pattern support this flow; a general API-key package does not provide the device lifecycle, atomic enrollment or recovery semantics and is not added merely to parse a bearer header. `Microsoft.Extensions.Http` provides the managed handler pool, and Microsoft's MIT-licensed `System.Security.Cryptography.ProtectedData` implements Windows DPAPI. See [ASP.NET Core authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/?view=aspnetcore-10.0), [EF Core concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) and [ProtectedData](https://www.nuget.org/packages/System.Security.Cryptography.ProtectedData/10.0.14).
