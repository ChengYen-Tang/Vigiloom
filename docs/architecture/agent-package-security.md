# Agent package trust and delivery

REQ-21 owns the publisher-authenticated package catalogue and central package library. REQ-20 owns Agent assignments, updater state, installation, rollback and their end-to-end acceptance. An accepted publisher signature does not prove a package is assigned to a device, is still permitted by the central policy, or is compatible with the machine.

## Trust chain

The publisher maintains TUF root, timestamp, snapshot and targets metadata. The initial root must come from the trusted installation or platform distribution, independently of the update endpoint. Private release keys do not belong on the central platform or the Agent. Root rotation is sequential and authenticated by the previous and new roots; timestamp and snapshot authority changes reset their trusted version baselines as part of the same durable root update. The central platform retains each verified root so a long-offline Agent can advance through intermediate versions. The installation must provide a bootstrap root whose subsequent history is available; the latest root alone cannot reconstruct missing history.

An Administrator can initialize an empty central trust store through the package-source trust API using the root and its SHA-256 fingerprint obtained through an independent trusted channel. Initialization checks the fingerprint, required roles and root self-signature, and atomically records the initialization in the operation audit. Self-signature and hash matching do not identify the publisher: the independent source is essential. Existing trust cannot be overwritten through this operation. An expired bootstrap root may be initialized so that the regular TUF update can traverse its signed successors; the final root must be current before catalogue verification succeeds. The official production root and its distribution are part of the release process and are not supplied by this API.

The SQL-backed central store serializes metadata refreshes with a session-scoped lock. Accepted metadata and invalidation of the previously published catalogue commit atomically; accepted root history is committed in that transaction. A failed later fetch never rolls back an accepted root. If a root version at or below the current root is missing, the Agent metadata endpoint reports temporary unavailability rather than a 404, because TUF treats a missing next root as the end of rotation. A higher, genuinely unpublished root version may return 404.

The updater can use an independently provisioned local SQLite trust store in a directory protected by its service identity. It must retain the database and its lock across restarts and must fail closed on missing or corrupt state. The checksum detects accidental damage, not replacement of both state and checksum by a privileged operator or restoration of a complete old database backup; operating-system access control and backup/recovery policy are required. Neither the central nor local store silently reinstalls a bootstrap root after an existing store is lost.

## Publisher data

The central-only `catalog.json` is a TUF target with schema version 1. Its entries contain a normalized version, runtime identifier, byte length, SHA-256 archive digest, SHA-256 digest of the per-package manifest and an explicit revoked flag. Permitted runtime identifiers follow REQ-17: `win-x64`, `win-x86` and `linux-x64`. An existing version/runtime pair cannot change either digest or byte length. A removed or revoked entry is not eligible for a new download, even if archive bytes remain cached.

Each package also has a separate TUF target named `<manifest-sha256>.json`. The manifest binds the version, runtime identifier, archive size and digest, minimum Updater version and optional inclusive Agent version bounds. With consistent snapshots, the repository may prefix this target name with the target hash. Agent-facing `targets` metadata must be the original publisher-signed metadata and use opaque identifiers: the central platform must not rewrite it to filter entries. It can reveal the number and hash relationship of targets, but must not disclose the central catalogue or return arbitrary manifests or archives to an Agent merely because it knows their hashes.

The central platform verifies the catalogue; an Agent obtains only its currently authorized manifest and archive. The manifest must match the catalogue entry and the archive must match the signed size and hash. The updater independently verifies publisher metadata, manifest and bytes, checks its actual platform and compatibility, and applies the separate assignment revision, revocation and rollback policy. The platform must check the current Agent credential, device generation, assignment, compatibility and policy immediately before serving a manifest or archive. A signed catalogue or manifest alone is not a download authorization.

The publisher stages metadata separately from immutable content-addressed archive objects. A metadata-only refresh does not recopy historical archives. Before advancing the authoritative publication pointer, the release workflow must ensure all newly referenced archives are durably available, preserve existing objects, compare the previous authoritative state and use a serialized compare-and-swap update. A staged directory alone is not a deployment, and GitHub Pages or a public Git branch is not the private Agent download authorization boundary.

`tools/agent-release/repository_store.py` provides a single-host filesystem publication option. Its `--expected` argument is the previously read `current` generation digest, or `none` for the first publication. It checks the signed candidate, its expiry, monotonic root history, existing package identities, and the presence and size of all referenced objects before switching the pointer. New or previously uncommitted objects are hashed before being committed. Existing objects recorded in the signed previous generation are not rehashed during each metadata refresh; the private store must prevent unauthorized modification, and consumers still verify the archive digest. Use `--audit` for an explicit full-hash integrity check and `--repair <archive> --sha256 <digest>` to restore a currently referenced object only from bytes matching its signed identity. If replacement fails after partially moving files, inspect both paths reported by the command before retrying; the verified staging copy is not intentionally deleted. Full audits hold the publisher lock and should be scheduled as maintenance. Old generations and packages are retained, including unreferenced files left by an interrupted publication; deleting them requires a separate retention process that respects assignment and rollback references.

This filesystem option assumes a protected local filesystem on one publisher host, with all writers using its lock. It is not a distributed CAS protocol for NFS, SMB or multiple publisher machines. Files are flushed before the pointer switch; on Unix the containing directories are also synced. Python does not provide an equivalent portable directory flush on Windows here, so process interruption recovery is tested but Windows power-loss durability is not established. Back up the store and protect against rollback of the whole filesystem.

`tools/agent-release/origin.py` is an optional read-only origin for that store. It requires a separate `VIGILOOM_ORIGIN_READ_TOKEN`, binds to loopback by default and serves only fixed metadata, target and content-addressed package paths. Waitress does not terminate TLS: expose it only behind a correctly configured HTTPS reverse proxy on a protected network, and give the origin account read-only store permissions. The origin token is for the central platform, not an Agent credential; the publisher writes with separate filesystem privileges.

The manually dispatched `.github/workflows/agent-release.yml` builds self-contained Agent archives for `win-x64`, `win-x86` and `linux-x64` on hosted runners. A separate dedicated Linux runner labeled `vigiloom-release` signs and publishes from the `master` branch. Configure the `agent-release` GitHub environment with `VIGILOOM_TARGETS_KEY_PEM`, `VIGILOOM_SNAPSHOT_KEY_PEM`, `VIGILOOM_TIMESTAMP_KEY_PEM` and, for encrypted keys, `VIGILOOM_RELEASE_KEY_PASSWORD` as secrets. Environment variables `VIGILOOM_RELEASE_STORE` and `VIGILOOM_RELEASE_BOOTSTRAP` identify absolute paths outside the checkout; `VIGILOOM_RELEASE_INITIAL` identifies the initial public root repository for the first publication, and optional `VIGILOOM_RELEASE_ROOT_UPDATES` points to a directory containing only public root history updates. The runner must be dedicated, trusted and on the same publisher host as the store; its account needs store write access. Keep the root signing key offline and do not place any release private key in the central platform or origin.

The workflow can release a version, refresh metadata or revoke a `VERSION@RID` entry. Once the publisher is configured, set the repository variable `VIGILOOM_RELEASE_AUTOMATIC` to `true` to enable a scheduled metadata refresh every six hours; it is disabled until explicitly configured. Monitor failed or delayed runs: timestamp metadata expires after one day. The workflow reads the current generation before preparing the next and fails rather than overwrite a concurrent publication. If the workflow reports an uncertain publication outcome, inspect the store's `current` pointer before retrying. The workflow and origin are implementation options, not a required deployment topology. Official production keys, an independently distributed bootstrap root, the dedicated runner and HTTPS origin still need provisioning; an actual cross-platform signed release through that environment has not yet been validated.

## Transport and local cache

Metadata and manifests are bounded to 1 MiB per document. Package transfer streams to a private staging file with a signed size bound and SHA-256 verification before it can become a cache entry; incomplete and corrupt downloads are not exposed as verified files. Transient HTTP failures are retried a limited number of times, respecting bounded `Retry-After`. Metadata and package requests use pooled HTTPS connections with automatic redirects disabled, and Agent credentials are attached only to individual requests.

The package cache is node-local and private to the platform service. Its quota includes stored package files; downloads are serialized under a local filesystem lock and require room for the full signed size. Interrupted staging files are removed under that lock. Cache hits are verified before being returned. Assignment-aware retention, deletion protection, authorization, release publication and the actual update flow must be wired and validated before REQ-21/REQ-20 claim full delivery.

An Administrator may request cache population for a currently listed, non-revoked package. The central platform verifies the per-package manifest and checks the source revision and current catalogue eligibility both before and after transfer; caching does not grant download access. `Vigiloom:AgentPackages:CachePath` selects the private node-local directory. The default is `Vigiloom/agent-packages` under the service account's local application-data directory; where that directory is unavailable, set an explicit path. `Vigiloom:AgentPackages:CacheQuotaBytes` sets the per-node quota, defaulting to 5 GiB. The hosting account must have private read/write access, and separate nodes need separate cache directories. Quota exhaustion fails the request; automatic assignment-aware eviction is not yet implemented.
