# REQ-11 Speedtest.net execution

- The central Worker uses the pinned MIT-licensed `NetPace.Core` library to retrieve the Speedtest.net server list, select a reachable candidate by HTTP latency, and measure download. Live upload uses Vigiloom's own continuous HTTP lanes. This is a third-party client and is not the official Ookla CLI. Provider use remains subject to the user's applicable terms.
- Discovery first requests `https://www.speedtest.net/api/js/config-sdk` for provider-suggested candidates. This endpoint is not verified as a supported public API; its client authentication token and ISP IDs are not used. If it is unavailable, invalid, empty, or yields no reachable candidate, the existing HTTPS static directory is used as a fallback, subject to the same overall timeout and traffic budget. In automatic multi-server mode the first 10 valid, distinct candidates are measured concurrently with a five-second screening deadline. At least one successful request and a valid latency are required; successful candidates are sorted by latency, with the fastest as primary and up to three more used for download. It does not add untested servers if fewer than four are reachable. Single-server selection uses NetPace's existing screening. No ISP matching or throughput ranking is assumed. Sockets resolve public addresses and connect to the resolved address, with proxy and automatic redirects disabled. The client permits only the discovery hosts and the candidate hosts. Speedtest.net's directory includes HTTP endpoints; such measurements are not encrypted. Do not describe this integration as an official Ookla engine or assume identical measurements.
- Download and upload have phase budgets, and a shared counter limits request and response bodies across discovery and measurements. Reaching a phase's planned budget is normal completion if both phases have sufficient duration and successful requests; only exhaustion of the shared total is reported as `BudgetExceeded`. Concurrent requests wait for outstanding reservations to finish before deciding that the budget is exhausted; unused reservations return to the pool. HTTP headers, transport overhead, buffering and partially failed writes are not fully captured: actual wire use can exceed the configured value. Cancellation and a whole-operation timeout stop new work; failure, short tests or total budget exhaustion are not presented as a full successful measurement or as zero Mbps.
- Tests run automatically on a schedule by default; the Administrator can adjust or disable scheduling and optionally set traffic and timeout limits. There is no manual-start endpoint. SQL leases, cancellation and idempotency remain coordinated across Workers; Read only users can inspect private history. REQ-39 owns retention and scheduled cleanup; these are not yet implemented for speed results, so history currently remains until separately removed.
- Local automated tests do not contact the external provider. Real measurements and comparison with an appropriate reference are required before acceptance; measured results must include conditions and must not be presented as evidence of universal accuracy.

## Accuracy evaluation

- `NetPace.Core` 0.28.0 was published on 2026-10-21; inspect the [matching source tag](https://github.com/FrankRay78/NetPace/tree/0.28.0), not a later development branch. It implements HTTP payload transfers. For a single-server completed download batch, Vigiloom divides observed download bytes by NetPace's transfer duration. For automatic multi-server download, it counts all received bytes over the common wall-clock duration of each concurrent batch; it does not add the overlapping per-server durations. For download and upload it excludes the first third of valid samples (rounding the number retained up), sorts the remaining samples by rate, and selects the fastest 30% (rounding up to at least one). The reported rate is selected bytes divided by selected transfer time. Download uses variable-duration batch samples; continuous upload uses roughly 500 ms windows of successfully confirmed payload bytes. Upload completions can arrive in bursts and do not represent a wire-level traffic trace. A small sample count may mean that one sample determines the result. This experimental method is not verified as the official engine's algorithm and can overestimate typical throughput. The upload endpoint probe is excluded from the transfer windows and cannot satisfy the minimum transfer duration. An empty or otherwise invalid batch makes the measurement incomplete. When a phase times out, a partially received download with measurable wall duration is included as a batch sample; upload samples count only successfully confirmed requests. Download counts include received bytes from requests cancelled when a phase cap is reached; the separate traffic counter includes uploaded bytes even if their requests are not confirmed. Excluding unconfirmed uploads can underestimate actual throughput, and an HTTP response alone cannot prove how the remote server handled the data. Its method and server selection are not the official Speedtest engine.
- The library's server directory supplies the test server sponsor and location, not the originating connection's ISP. The detail page therefore shows unavailable for client ISP until a trustworthy supported source is integrated; it must not substitute the server sponsor for the client ISP.
- NetPace 0.28.0 requires latitude and longitude attributes while parsing the directory; a missing or malformed attribute can fail directory parsing. Finite coordinates inside geographic bounds are saved and displayed; otherwise neither coordinate is reported. A missing-coordinate display does not imply the library can measure a server whose directory entry omitted those attributes.
- Local tests verify conversion, incomplete results, cancellation and the shared body budget; they cannot establish the accuracy of an Internet measurement. Automatic mode targets 15 seconds per direction, downloads from the primary and up to three other candidates, and uploads to the primary. It starts with four parallel requests and can grow during the first half to a maximum of six per server, 24 total for download and six for upload. The adaptive rule is a bounded approximation, not a claim of matching the official client. Concurrent downloads share one wall-clock interval, transport and traffic budget; faster servers continue issuing requests until the shared batch target is reached, when outstanding requests are cancelled and their received bytes are retained in the traffic count. The displayed and persisted server is the primary, not a complete list of all download servers. Explicit server-ID measurements remain single-server with four requests. Success requires both directions to reach the target. Batch sizes are estimated for at most three seconds at the observed throughput; a slowdown can still lengthen a batch. Production budgets (up to 2048 MiB total, with half allocated to each direction) and timeouts (up to 60 seconds overall, with a per-phase deadline of up to 28 seconds) can prevent completion, particularly on fast links; incomplete measurements remain partial or timed out. The standalone SpeedLab uses a 4096 MiB lease for comparison without changing product settings.
- A successful transfer shorter than NetPace's millisecond resolution is counted as traffic but excluded from the speed calculation. The next batch grows within the remaining phase budget; the measurement still needs sufficient timed samples before it can succeed.
- The live HTTP upload resolves the legacy server upload endpoint once, then runs independent persistent request lanes. A lane sends its next request after a successful response, with payload size adapted to observed confirmed throughput and bounded from 50,000 bytes to 4 MiB. It starts four lanes and may add up to two more during the first half of the phase based on confirmed throughput in automatic multi-server mode. Each lane reserves its payload against a per-direction plan; a shared transport budget also accounts for HTTP bodies. In-flight requests are cancelled at the target duration and only completed successful payloads are used for rates. This approximates aspects of the inspected client; it does not implement its pipeline, `/upload` protocol, or remote server statistics. Request cancellations at the end and response latency can affect the outcome. Real traffic traces and repeated comparisons are needed to evaluate stability.
- If every request for a larger download asset returns HTTP 404 or 410, the same measurement tries the next smaller known image and keeps that ceiling for later batches. Other HTTP statuses, transport errors, mixed responses and cancellation are not treated as missing assets; the shared traffic and time limits still apply. File availability on actual providers remains to be verified.
- An initial Windows test on 2026-11-02, before the shared body-budget correction, reached the Keelung `klv3-1.speedtest.idv.tw` server and reported 194.97 Mbps down and 395.69 Mbps up with a 20 MiB configured budget. It reached that budget and exceeded it before the correction; no reference measurement was captured. This single run demonstrates connectivity only, and is not an accuracy result.
- Acceptance requires repeated, non-overlapping comparisons from the same location to the same Speedtest server, with elapsed times, budget, network load and provider versions recorded. Report differences and the observed conditions, not universal equivalence to the official product. The server sponsor and Speedtest server ID are retained with each result to make this comparison possible.

### Offline shared-bandwidth experiment

- On 2026-11-02, the [offline speed lab](../../tools/Vigiloom.SpeedLab/README.md) used an in-memory handler, a shared scheduler per direction, four concurrent requests, a 2048 MiB total content budget and a 60-second overall timeout. It modeled download payload sizes of 1, 2.25, 4, 9 and 16 million bytes for the five existing image names; these are **synthetic** sizes, not observations of provider files. Windows timer precision was temporarily set to 1 ms for the experiment. No provider endpoint was contacted.
- With configured bottlenecks of 890/244 Mbps and no extra request delay, two runs after adapting request sizes reported 880.37/236.01 and 884.36/237.18 Mbps; the fixture's separate observed rates were 882.50/236.27 and 886.07/236.94 Mbps. Their timing windows differ, so these are comparisons of the observed experiment rather than an accuracy certification.
- With an additional 50 ms delay per request, before the change two runs reported 445.63/153.47 and 454.75/152.27 Mbps. After the change they reported 773.93/201.29 and 775.64/199.15 Mbps; the independent observed rates were 792.08/191.66 and 793.79/189.85 Mbps. Four connections and request delays still prevented saturation of the configured bottleneck.
- With 10/5 Mbps bottlenecks and 50 ms per request, two runs reported approximately 9.84/4.86 Mbps. These fixtures do not model TCP, TLS, packet loss, provider processing, or official Speedtest behavior. `Success` means the configured measurement completed; it does not establish that available bandwidth was saturated or that an external comparison passed.
