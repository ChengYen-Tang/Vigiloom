# REQ-11 Speedtest.net execution

- The central Worker uses the pinned MIT-licensed `NetPace.Core` library to retrieve the Speedtest.net server list, select a reachable candidate by HTTP latency, and measure download and upload. It is a third-party client and is not the official Ookla CLI. Provider use remains subject to the user's applicable terms.
- Discovery uses the HTTPS Speedtest.net directory. Up to 20 supplied candidates are screened; sockets resolve public addresses and connect to the resolved address, with proxy and automatic redirects disabled. The client permits only the directory host and the candidate hosts. Speedtest.net's directory includes HTTP endpoints; such measurements are not encrypted. Do not describe this integration as an official Ookla engine or assume identical measurements.
- Download and upload have phase budgets, and a shared counter limits request and response bodies across discovery and measurements. Reaching a phase's planned budget is normal completion if both phases have sufficient duration and successful requests; only exhaustion of the shared total is reported as `BudgetExceeded`. Concurrent requests wait for outstanding reservations to finish before deciding that the budget is exhausted; unused reservations return to the pool. HTTP headers, transport overhead, buffering and partially failed writes are not fully captured: actual wire use can exceed the configured value. Cancellation and a whole-operation timeout stop new work; failure, short tests or total budget exhaustion are not presented as a full successful measurement or as zero Mbps.
- Tests run automatically on a schedule by default; the Administrator can adjust or disable scheduling and optionally set traffic and timeout limits. There is no manual-start endpoint. SQL leases, cancellation and idempotency remain coordinated across Workers; Read only users can inspect private history. REQ-39 owns retention and scheduled cleanup; these are not yet implemented for speed results, so history currently remains until separately removed.
- Local automated tests do not contact the external provider. Real measurements and comparison with an appropriate reference are required before acceptance; measured results must include conditions and must not be presented as evidence of universal accuracy.

## Accuracy evaluation

- `NetPace.Core` 0.28.0 was published on 2026-10-21; inspect the [matching source tag](https://github.com/FrankRay78/NetPace/tree/0.28.0), not a later development branch. It implements HTTP payload transfers; for completed batches, Vigiloom divides observed download bytes or upload bytes from successfully completed requests by the sum of NetPace's transfer durations. Upload endpoint probes and time between batches are excluded from this calculation and cannot satisfy the minimum transfer duration. An empty or otherwise invalid batch makes the measurement incomplete. When a phase times out, a partially received download may yield a wall-time estimate; interrupted uploads retain only a previously completed estimate because their probe time cannot be separated reliably. Download counts include received bytes from requests cancelled when a phase cap is reached; the separate traffic counter includes uploaded bytes even if their requests are not confirmed. Excluding unconfirmed uploads can underestimate actual throughput, and an HTTP response alone cannot prove how the remote server handled the data. Its method and server selection are not the official Speedtest engine.
- The library's server directory supplies the test server sponsor and location, not the originating connection's ISP. The detail page therefore shows unavailable for client ISP until a trustworthy supported source is integrated; it must not substitute the server sponsor for the client ISP.
- NetPace 0.28.0 requires latitude and longitude attributes while parsing the directory; a missing or malformed attribute can fail directory parsing. Finite coordinates inside geographic bounds are saved and displayed; otherwise neither coordinate is reported. A missing-coordinate display does not imply the library can measure a server whose directory entry omitted those attributes.
- Local tests verify conversion, incomplete results, cancellation and the shared body budget; they cannot establish the accuracy of an Internet measurement. Four concurrent transfers and a two-second minimum are safeguards, not proof that the link reached its capacity.
- An initial Windows test on 2026-11-02, before the shared body-budget correction, reached the Keelung `klv3-1.speedtest.idv.tw` server and reported 194.97 Mbps down and 395.69 Mbps up with a 20 MiB configured budget. It reached that budget and exceeded it before the correction; no reference measurement was captured. This single run demonstrates connectivity only, and is not an accuracy result.
- Acceptance requires repeated, non-overlapping comparisons from the same location to the same Speedtest server, with elapsed times, budget, network load and provider versions recorded. Report differences and the observed conditions, not universal equivalence to the official product. The server sponsor and Speedtest server ID are retained with each result to make this comparison possible.
