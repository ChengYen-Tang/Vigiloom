# Agent transport: implementation notes

REQ-19 is in progress. The queue, authenticated receipt endpoint and scheduled Agent sender exist; no production collector produces batches yet. This document does not claim the end-to-end transport is complete.

## Local durable queue

The queue stores the exact serialized batch bytes, its UUID v7 batch ID, first enqueue time, record count and local insertion order. It is bound to one registered Agent ID: a different identity must not drain an existing identity's queue. The local database lives in the existing protected Agent state directory, outside version-specific installation folders. The existing identity lease protects each database operation across processes; a queue instance serializes its own operations. The host must coordinate queue operations with other users of the identity lease, including credential rotation, and handle a busy lease without losing a batch.

The queue uses Microsoft.Data.Sqlite 10.0.14 and the bundled SQLite native library pinned to 3.53.3. SQLite's upstream WAL documentation records a concurrency corruption bug fixed in 3.51.3 and supported backports; the queue uses rollback journaling and synchronous FULL, not WAL. The database and its transient journal remain in the protected directory; SQLite connections are disposed after each operation and pooling is disabled so the lease is not released with a connection still open. Transactions atomically change a batch and the stored capacity counters. Unknown future database formats are rejected before modifying them.

The initial capacity is 256 MiB of serialized payload and at most 8,192 queued batches. This is a **logical payload limit**, not a hard filesystem quota: SQLite pages, metadata and a rollback journal add disk use. A full queue rejects the new batch so the caller can apply backpressure; rejection is not yet a durable loss count and no policy for discarding or expiry is implemented in this slice. The host must expose available capacity, persist and report any actual loss, distinguish classes of data, and handle disk-full and filesystem errors without reporting success. User-adjustable limits and explicit retention/expiry behavior remain to be integrated.

Queue format 2 atomically upgrades format 1 and adds persistent quarantine markers. Invalid local batches and batches rejected with permanent HTTP client errors remain in the database with their bytes and reason, still consume capacity, and are skipped when reading the next pending batch. Heartbeats report queue counts to the central platform; detailed quarantine diagnosis and recovery through the UI are not yet implemented. Older format-1 binaries reject the format-2 database: the future updater must check compatibility and must not start an incompatible downgrade. Quarantine is not deletion, expiry, or a durable loss counter.

## Queue status reports

An Agent process obtains a fresh report epoch using an authenticated compare-and-swap against the central epoch. A lost session response is retried with the same expected and proposed epochs. Each process serializes snapshots and assigns an increasing sequence. The central transaction accepts only the current epoch and a newer sequence; old or duplicate reports do not replace the snapshot. If another process replaces the session, the old process keeps sending empty heartbeats and does not automatically take the session back. A failed or timed-out session negotiation likewise does not stop heartbeat delivery. A null queue snapshot means the local queue could not be read, not that it was empty. A report timestamp must be considered when presenting queue status; current connectivity does not make an old snapshot fresh.

This is not a complete restore protocol. Restoring the central database can roll an epoch and its watermark back. REQ-40 must fence existing report sessions and clear their snapshots before accepting traffic after a restore, then establish a safe way for Agents to resume queue reporting, and verify the full restore flow. A fenced running process currently continues only empty heartbeats until restarted. The current implementation does not yet provide or validate the restore operation. Queue UI, lost-data accounting, and configurable limits remain incomplete under REQ-19.

## Required integration

- Version 1 batches currently accept only validated `agent.runtime.v1` observations, with stable message IDs, order, and bounded strings; they are not a general telemetry protocol. The central transaction revalidates the machine credential and device binding, stores structured observations and a SHA-256 receipt for the exact payload bytes, and acknowledges only after commit. Identical retries are acknowledged; a batch ID or message ID reused with different content is rejected. The original wire payload is not stored centrally. The Agent host uses a factory-managed HTTP client without cookies or automatic redirects; it preserves local bytes after a lost acknowledgement and removes them only on HTTP 204. The scheduled sender is integrated, but no production collector creates these batches yet.
- The sender works on one batch at a time with a 5–6 second normal interval, exponential retry with jitter and a five-minute automatic backoff ceiling. An explicit Retry-After can extend that wait, even beyond a single timer's maximum. A stop cancels pending waits and requests without treating cancellation as confirmation. Queue and heartbeat operations briefly retry identity-lease contention; no transport operation holds that lease over its HTTP request. A simulated 60-day Retry-After covers slicing and cancellation, not elapsed real-world waiting. Restart recovery and production backlog catch-up require further validation.
- The receipt store temporarily caps each Agent at 8,192 receipts and 256 MiB of summed original payload lengths, not actual database disk usage. There is no receipt cleanup yet; reaching the cap blocks new batches while still permitting a retry of a previously accepted batch. This is a temporary safety bound, not the required retention policy. Do not repackage expired batches with new IDs to bypass the replay window.
- Heartbeat and batch requests use a process-local bounded pre-authentication concurrency gate and a per-verified-Agent rate limit. Invalid credentials do not create attacker-chosen rate-limit partitions. These are safeguards, not evidence of 500-Agent capacity, cross-instance coordination, or fairness under slow requests; measure and adjust against actual deployment load.
- Define and implement the 24-hour accepted replay window, seven-day inbox retention, clock-skew handling and grace period together. An Agent-supplied timestamp alone cannot prove when a batch was created; inbox cleanup must not allow an expired or previously committed batch to be accepted as new. Configuration changes must preserve old-generation guarantees.
- Apply bounded batching, retries, cancellation, compression and payload size checks on both endpoints. Monitor and expose missing data, loss counts, queue pressure and last successful send without storing credentials in the queue.
- Heartbeats send immediately at host startup and use the effective interval without overlapping requests; the built-in default is 30 seconds. The receiver stores server receipt time only after checking the current credential and device generation within the commit transaction. A pending credential rotation still needs explicit recovery; automatic rotation reconciliation is not implemented.
- Agent connectivity is separate from device Ping. The initial offline threshold is 90 seconds and widens before the server issues a longer heartbeat interval; it does not yet shrink after an interval decrease. Startup and jittered polling, last-good transport settings, administrator controls and read-only status have a partial implementation; remaining configuration groups, full cross-host and UI acceptance, and safe threshold reduction are tracked in [agent configuration](agent-configuration.md).
- Validate actual process termination, restart, simultaneous submissions, acknowledgment loss, migration/downgrade compatibility, Windows service accounts, Windows x86, Linux x64 and applicable filesystems. SQLite FULL relies on operating-system and storage guarantees; tests must not claim hardware power-loss durability without evidence.

References: [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous), [Microsoft.Data.Sqlite locking](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/database-errors).
