# Agent transport: implementation notes

REQ-19 is in progress. The queue, authenticated receipt endpoint and scheduled Agent sender exist; no production collector produces batches yet. This document does not claim the end-to-end transport is complete.

## Local durable queue

The queue stores the exact serialized batch bytes, its UUID v7 batch ID, first enqueue time, record count and local insertion order. It is bound to one registered Agent ID: a different identity must not drain an existing identity's queue. The local database lives in the existing protected Agent state directory, outside version-specific installation folders. The existing identity lease protects each database operation across processes; a queue instance serializes its own operations. The host must coordinate queue operations with other users of the identity lease, including credential rotation, and handle a busy lease without losing a batch.

The queue uses Microsoft.Data.Sqlite 10.0.14 and the bundled SQLite native library pinned to 3.53.3. SQLite's upstream WAL documentation records a concurrency corruption bug fixed in 3.51.3 and supported backports; the queue uses rollback journaling and synchronous FULL, not WAL. The database and its transient journal remain in the protected directory; SQLite connections are disposed after each operation and pooling is disabled so the lease is not released with a connection still open. Transactions atomically change a batch and the stored capacity counters. Unknown future database formats are rejected before modifying them.

The initial capacity is 256 MiB of serialized payload and at most 100,000 queued batches. The count leaves headroom for 24 hours at one batch per second, but the byte limit or bursts may fill the queue sooner; it is not a guarantee of 24-hour storage. This is a **logical payload limit**, not a hard filesystem quota: SQLite pages, metadata and a rollback journal add disk use. Administrators can configure platform and device limits, which Agents synchronize independently; see [agent configuration](agent-configuration.md). A full queue rejects the new batch so the caller can apply backpressure; rejection is not yet a durable loss count and no policy for discarding or expiry is implemented in this slice. The host must expose available capacity, persist and report any actual loss, distinguish classes of data, and handle disk-full and filesystem errors without reporting success. Explicit retention/expiry behavior remains to be integrated.

Queue format 2 atomically upgrades format 1 and adds persistent quarantine markers. Invalid local batches and batches rejected with permanent HTTP client errors remain in the database with their bytes and reason, still consume capacity, and are skipped when reading the next pending batch. Heartbeats report queue counts and an optional reason breakdown; batch-level inspection and recovery through the UI are not yet implemented. Older format-1 binaries reject the format-2 database: the future updater must check compatibility and must not start an incompatible downgrade. Quarantine is not deletion, expiry, or a durable loss counter.

### Quarantine diagnostics (REQ-19)

Report an optional, bounded breakdown of retained quarantined batches by the existing fixed rejection categories. Read the queue totals and breakdown under the same identity lease, without reading payload bytes, and mark unsupported stored rejection values separately. The central platform accepts only non-negative, internally consistent counts, and applies them with the existing authenticated session and monotonically ordered queue snapshot. Missing details from an older Agent or an unreadable queue mean unknown, not zero; a full queue and quarantined retained bytes are not evidence of data loss. Show reasons and counts to authenticated monitoring readers, without exposing payloads, credentials or raw error text. This is diagnosis, not an instruction to delete, repack, retry or clear a batch.

During rolling upgrades, an older server that rejects the new optional field receives a bounded retry without that field, followed by the existing configuration fallback when needed. Central storage ties the summary to its own epoch and sequence; an older server can update the queue without clearing newer columns, so the summary is shown only while both markers still match the current queue report. Tests cover unknown values, missing reports, ordering and fallback; batch-level diagnosis and actual loss reporting remain incomplete.

The Agent treats a batch endpoint HTTP 410 response as an expired-batch rejection and preserves the original bytes with an expiry quarantine reason instead of retrying indefinitely or acknowledging them. The receiver does not yet issue 410, so this client behavior alone does not implement or verify the 24-hour replay window.

## Queue status reports

An Agent process obtains a fresh report epoch using an authenticated compare-and-swap against the central epoch. A lost session response is retried with the same expected and proposed epochs. Each process serializes snapshots and assigns an increasing sequence. The central transaction accepts only the current epoch and a newer sequence; old or duplicate reports do not replace the snapshot. If another process replaces the session, the old process keeps sending empty heartbeats and does not automatically take the session back. A failed or timed-out session negotiation likewise does not stop heartbeat delivery. A null queue snapshot means the local queue could not be read, not that it was empty. A report timestamp must be considered when presenting queue status; current connectivity does not make an old snapshot fresh.

This is not a complete restore protocol. Restoring the central database can roll an epoch and its watermark back. REQ-40 must fence existing report sessions and clear their snapshots before accepting traffic after a restore, then establish a safe way for Agents to resume queue reporting, and verify the full restore flow. A fenced running process currently continues only empty heartbeats until restarted. The current implementation does not yet provide or validate the restore operation. Queue status and configurable limits are available; complete loss accounting and the remaining queue workflows are still outstanding under REQ-19.

## Required integration

- Version 1 batches currently accept only validated `agent.runtime.v1` observations, with stable message IDs, order, and bounded strings; they are not a general telemetry protocol. The central transaction revalidates the machine credential and device binding, stores structured observations and a SHA-256 receipt for the exact payload bytes, and acknowledges only after commit. Identical retries are acknowledged; a batch ID or message ID reused with different content is rejected. The original wire payload is not stored centrally. The Agent host uses a factory-managed HTTP client without cookies or automatic redirects; it preserves local bytes after a lost acknowledgement and removes them only on HTTP 204. The scheduled sender is integrated, but no production collector creates these batches yet.
- The sender works on one batch at a time with a 5–6 second normal interval. After a confirmed delivery it can continue with 250 ms gaps for a maximum of four consecutive batches, then waits the normal interval; an empty or rejected queue also returns to the normal interval. This bounded catch-up allows the sender to drain a backlog without overlapping requests. Temporary errors use exponential retry with jitter and a five-minute automatic backoff ceiling; an explicit Retry-After can extend that wait, even beyond a single timer's maximum. A stop cancels pending waits and requests without treating cancellation as confirmation. Queue and heartbeat operations briefly retry identity-lease contention; no transport operation holds that lease over its HTTP request. Simulated timing does not establish production throughput or fairness; restart recovery and production backlog catch-up require further validation.
- The receipt store temporarily caps each Agent at 8,192 receipts and 256 MiB of summed original payload lengths, not actual database disk usage. There is no receipt cleanup yet; reaching the cap blocks new batches while still permitting a retry of a previously accepted batch. This is a temporary safety bound, not the required retention policy. Do not repackage expired batches with new IDs to bypass the replay window.
- Heartbeat and batch requests use a process-local bounded pre-authentication concurrency gate and a per-verified-Agent rate limit. Invalid credentials do not create attacker-chosen rate-limit partitions. These are safeguards, not evidence of 500-Agent capacity, cross-instance coordination, or fairness under slow requests; measure and adjust against actual deployment load.
- Define and implement the 24-hour accepted replay window, seven-day inbox retention, clock-skew handling and grace period together. An Agent-supplied timestamp alone cannot prove when a batch was created; inbox cleanup must not allow an expired or previously committed batch to be accepted as new. Configuration changes must preserve old-generation guarantees.
- The Agent may gzip a batch when it reduces transfer size; if an older central platform rejects gzip with HTTP 415 it retries the same durable batch uncompressed. The receiver limits both request and decompressed size and hashes the decoded bytes, so compression does not change batch identity or deduplication. The Web process enables the .NET 10 runtime's `System.IO.Compression.UseStrictValidation` AppContext switch before startup: without it, a truncated gzip footer can be accepted after producing a complete JSON body. This switch affects all compressed input decoded in the Web process, not just Agent traffic; it is an implementation switch in the current [runtime source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.IO.Compression/src/System/IO/Compression/DeflateZLib/DeflateStream.cs), so runtime upgrades and all Web decompression paths require regression testing. It is not a claim that every possible trailing byte is rejected. Bounded retries and cancellation are implemented; exposing missing data, loss counts, queue pressure and last successful send remains incomplete. Never store credentials in the queue.
- Heartbeats send immediately at host startup and use the effective interval without overlapping requests; the built-in default is 30 seconds. The receiver stores server receipt time only after checking the current credential and device generation within the commit transaction. A pending credential rotation still needs explicit recovery; automatic rotation reconciliation is not implemented.
- Agent connectivity is separate from device Ping. The initial offline threshold is 90 seconds and widens before the server issues a longer heartbeat interval; it does not yet shrink after an interval decrease. Startup and jittered polling, last-good transport settings, administrator controls and read-only status have a partial implementation; remaining configuration groups, full cross-host and UI acceptance, and safe threshold reduction are tracked in [agent configuration](agent-configuration.md).
- Validate actual process termination, restart, simultaneous submissions, acknowledgment loss, migration/downgrade compatibility, Windows service accounts, Windows x86, Linux x64 and applicable filesystems. SQLite FULL relies on operating-system and storage guarantees; tests must not claim hardware power-loss durability without evidence.

## Pending replay and receipt-retention boundary

The following is a proposed integration boundary, not a description of deployed behavior. REQ-19 owns immutable batch identity, the authenticated transactional receiver, Agent retry and quarantine behavior, bounded offline storage, and observation of loss or clock errors. REQ-39 owns central receipt retention, bounded cleanup, and safe transitions when retention or replay settings are reduced. REQ-40 owns fencing after a central database restore. These deliverables require integration tests; completing an individual receipt or queue slice does not establish the seven-day guarantee.

For a new batch, the initial proposed acceptance window is 24 hours according to its persisted enqueue timestamp, with up to five minutes of future clock skew allowed. A previously committed batch with the same digest should receive the original success even after that window, while its receipt exists, so a lost acknowledgment can be resolved. The same ID with different bytes remains a conflict. New expired batches should receive HTTP 410 and remain preserved locally in quarantine, not be silently deleted or acknowledged. An Agent timestamp is not proof of when data was actually created, and cannot prevent an authenticated producer from repackaging or altering data after receipt cleanup.

Before enabling these rules, define a recoverable response for clocks ahead of the allowed skew, protect new-batch decisions against central clock rollback, and ensure that Agents which do not understand 410 cannot indefinitely block newer batches. The effective policy must also account for existing offline batches and earlier configuration promises; a runtime upgrade alone must not silently shorten a previously promised retry window. A central restore can roll back any stored clock or replay watermark and must follow the REQ-40 restore fencing procedure. No clock watermark, replay rejection, rollout negotiation or cleanup is implemented by this section.

For diagnosis, authenticated readers can see when the last committed batch's reported enqueue time is more than five minutes ahead of its platform receipt time. This is a historical comparison of two clocks, not proof of which clock is wrong or a live clock measurement; retries do not refresh it. The UI also flags a receipt timestamp later than the current platform time. These observations do not enforce the proposed replay window.

REQ-39 cleanup eligibility must use a fixed retention deadline and the acceptance windows and grace promised by all applicable generations. A duplicate acknowledgment while a receipt exists does not extend that deadline. Once the receipt has been cleaned, the receiver cannot confirm the original commit and must not fabricate a success; it must explicitly reject an unchanged expired batch rather than ingest it again. Tests must cover the cutoff, clock skew, lost acknowledgments, concurrent submissions and retention changes. The current per-Agent 8,192-receipt and summed-payload caps will block long before seven days at sustained high rates, and per-request receipt count/sum scans are not evidence of capacity for 500 Agents. Measure actual SQL throughput and storage before selecting limits or claiming the scale target.
