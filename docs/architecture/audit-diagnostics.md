# Shared operation audit: proposed REQ-38 foundation

This document describes a work-in-progress slice, not a claim that every Vigiloom operation is already audited. REQ-38 owns the shared audit contract, storage and authorized diagnosis. Individual modules own their operations and choose the allowed structured event for each one. REQ-39 owns retention and cleanup of ordinary audit records; the existing initial-administrator marker remains protected separately. Existing account, Agent and dashboard records remain owned by their respective modules; do not silently delete or present them as already migrated.

## Scope and privacy

Begin with a versioned, typed event for a real Administrator change to central network speed settings. The event contains the authenticated actor ID, resource ID and kind, server UTC time, action, result, and bounded, explicitly defined non-secret setting values and versions. It must not accept arbitrary request bodies, headers, credentials, user-supplied log messages, exception strings or unbounded dictionaries. Expand supported event kinds deliberately as their owners integrate them; unknown kinds or invalid values must not be silently stored as trusted events. No RowId is exposed as an API identity.

Modules produce versioned event types, and the central writer only accepts explicitly registered types with approved serializers. REQ-39 must add its typed retention-settings event through this contract, not duplicate the SQL writer or fall back to arbitrary JSON. Record both the previous and committed setting versions and effective values using the central server's time. A success records a committed change; it does not assert that a scheduler or Agent has already applied it. Concurrency/version checks prevent a stale repeat from creating a second successful change; do not claim general exactly-once delivery for unrelated future event producers.

The audit event and successful setting update commit in the same SQL transaction on the same target database. A stale version or validation failure cannot create a successful change event; a failed audit insert rolls back the setting update. Failures before commit need separately designed, sanitized diagnostic reporting; do not claim they have been atomically recorded by a rolled-back transaction. A failure to access the audit store is a failed operation, not a successful setting change.

An implementation in AlertingOperations owns the audit schema and migration, and exposes a narrow generic transactional writer through BuildingBlocks while event DTOs remain in shared Contracts. Browser-facing Contracts therefore do not expose database connections. The writer may use the caller's already-open database connection and transaction without taking ownership of either; do not open an independent connection and claim atomicity. Validate that connection and transaction are compatible, parameterize SQL and honor cancellation. A future retention setting can use the same contract without NetworkMonitoring or other modules writing directly to the audit table. Integrate migrations in the existing Migrator and register the implementation in the Web and Worker hosts as appropriate.

## Administrator query and evidence

Provide an Administrator-only, server-authorized bounded time-range query and an accessible UI showing operation, actor identity, resource, time, result and supported non-secret changes. Read only, anonymous and unrelated API or Agent credentials must not gain this management access. Fix a maximum time range and page depth, and use stable `(OccurredAt, RowId)` ordering; if cursors are introduced, keep the internal ordering key opaque and do not expose RowId as a permanent identity. Retain the actor ID even if the account is removed; do not add a foreign key that blocks legitimate account deletion. Add no generic arbitrary search of raw payloads. UI follows the existing visual system and must be designed and verified through Product Design for this requirement.

Acceptance of this slice requires real SQL Server/LocalDB migration, a real speed-settings change through authorized HTTP and its persisted event, transaction rollback on audit write failure, concurrent version conflict, cancellation, access boundaries and deliberate secret-exclusion cases. The speed setting is an existing product operation and must not contact the measurement provider. Verify Windows and Ubuntu CI. This slice does not complete REQ-38's remaining operational sources, dependency health matrix, full UI acceptance or REQ-39's data retention.
