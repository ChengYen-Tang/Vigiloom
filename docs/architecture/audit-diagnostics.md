# Shared operation audit: proposed REQ-38 foundation

This document describes a work-in-progress slice, not a claim that every Vigiloom operation is already audited. REQ-38 owns the shared audit contract, storage and authorized diagnosis. Individual modules own their operations and choose the allowed structured event for each one. REQ-39 owns retention and cleanup of ordinary audit records; the existing initial-administrator marker remains protected separately. Existing account, Agent and dashboard records remain owned by their respective modules; do not silently delete or present them as already migrated.

## Scope and privacy

Begin with a versioned, typed event for a real Administrator change to central network speed settings. The event contains the authenticated actor ID, resource ID and kind, server UTC time, action, result, and bounded, explicitly defined non-secret setting values and versions. It must not accept arbitrary request bodies, headers, credentials, user-supplied log messages, exception strings or unbounded dictionaries. Expand supported event kinds deliberately as their owners integrate them; unknown kinds or invalid values must not be silently stored as trusted events. No RowId is exposed as an API identity.

Existing account, API credential, device, Agent identity, Agent settings and scheduling audits remain in their owning schemas. Each owner supplies a bounded, date-indexed, allow-listed single-source projection; the Web host routes source selection without directly querying another module's storage. Unknown actions remain visible as unsupported without exposing their raw text. A source without an explicit outcome reports only that a record exists. Scheduling's accepted outcome describes the request rather than job completion. `/api/v1/operations/audit` continues to return speed events, with an additional nullable Ping field; `/api/v1/operations/audit/ping` separately returns Ping settings events. Both and the new source feed are Administrator-only and do not expose the internal RowId.

Central Ping setting changes use a separate allow-listed event containing the previous and current intervals, thresholds, concurrency limit and row versions. The first save can have an empty previous version. The setting, target rescheduling and event commit in one transaction; a failed audit write rolls back all three. The management page presents Ping as a distinct source and does not claim historical changes before this integration were recorded.

Modules produce versioned event types, and the central writer only accepts explicitly registered types with approved serializers. REQ-39 must add its typed retention-settings event through this contract, not duplicate the SQL writer or fall back to arbitrary JSON. Record both the previous and committed setting versions and effective values using the central server's time. A success records a committed change; it does not assert that a scheduler or Agent has already applied it. Concurrency/version checks prevent a stale repeat from creating a second successful change; do not claim general exactly-once delivery for unrelated future event producers.

The audit event and successful setting update commit in the same SQL transaction on the same target database. A stale version or validation failure cannot create a successful change event; a failed audit insert rolls back the setting update. Failures before commit need separately designed, sanitized diagnostic reporting; do not claim they have been atomically recorded by a rolled-back transaction. A failure to access the audit store is a failed operation, not a successful setting change.

An implementation in AlertingOperations owns the audit schema and migration, and exposes a narrow generic transactional writer through BuildingBlocks while event DTOs remain in shared Contracts. Browser-facing Contracts therefore do not expose database connections. The writer may use the caller's already-open database connection and transaction without taking ownership of either; do not open an independent connection and claim atomicity. Validate that connection and transaction are compatible, parameterize SQL and honor cancellation. A future retention setting can use the same contract without NetworkMonitoring or other modules writing directly to the audit table. Integrate migrations in the existing Migrator and register the implementation in the Web and Worker hosts as appropriate.

## Administrator query and evidence

Provide an Administrator-only, server-authorized bounded time-range query and an accessible UI showing operation, actor identity, resource, time, result and supported non-secret changes. Read only, anonymous and unrelated API or Agent credentials must not gain this management access. Fix a maximum time range and page depth, and use stable `(OccurredAt, RowId)` ordering; if cursors are introduced, keep the internal ordering key opaque and do not expose RowId as a permanent identity. Retain the actor ID even if the account is removed; do not add a foreign key that blocks legitimate account deletion. Add no generic arbitrary search of raw payloads. UI follows the existing visual system and must be designed and verified through Product Design for this requirement.

Acceptance of this slice requires real SQL Server/LocalDB migration, a real speed-settings change through authorized HTTP and its persisted event, transaction rollback on audit write failure, concurrent version conflict, cancellation, access boundaries and deliberate secret-exclusion cases. The speed setting is an existing product operation and must not contact the measurement provider. Verify Windows and Ubuntu CI. This slice does not complete REQ-38's remaining operational sources, dependency health matrix, full UI acceptance or REQ-39's data retention.

## Shared diagnostics and platform health: implementation boundaries

REQ-39 needs the shared audit, queryable diagnostics and health foundation before it can implement and verify its cleanup. The user has explicitly approved merging that foundation before REQ-38's cross-requirement acceptance; REQ-38 remains in progress until its promised integrations, including real REQ-39 cleanup, have been verified. This exception does not change the ownership of either requirement.

Use existing authoritative sources where they contain the information: Hangfire's monitoring API for persisted job failures and server heartbeats, and the scheduling module's Outbox state for current retry and terminal failures. Neither is a complete permanent failure history. Limit query size and return only approved fields, stable failure categories and identifiers needed to investigate; never return job arguments, exception text, credentials or raw message payloads. Pagination bounds response size but is not a storage limit. Existing Hangfire and Outbox retention remain their respective owners' responsibility and must be covered by REQ-39's cleanup rather than silently deleting active work.

Ping and speed scanner loop exceptions currently have no durable, queryable source. Store a bounded, structured summary of their state, including last success and last failure, failure category, and repeated-failure count; clearly label it as a summary, not a complete event history. Bound the number and size of records independently of failure frequency and ensure multiple Worker instances cannot overwrite each other's health as though they were one process. Establish exact bounds and stale-instance cleanup before implementing the store. A normal host shutdown cancellation is not a scanner failure. Diagnostic writes must not change a monitoring result or transaction outcome; use a short independent timeout, prevent recursive diagnostic failures, and use a sanitized log fallback if the database itself cannot persist the summary. A fallback is not a durable record and must not be reported as one.

Use at most 64 reusable Worker diagnostic slots as an initial platform limit, not a limit on monitored devices. Claim a free or expired slot atomically using database time, assign an ephemeral UUIDv7 boot identifier, and renew its lease independently of scanner execution. Every subsequent write must match both the slot and current boot identifier and must be rejected after the lease expires. Never evict a live slot; if all slots are occupied, monitoring continues while diagnostic registration reports its capacity failure. Reusing an expired slot removes its old summary; this bounded current-state store is not a substitute for retention of audit or diagnostic history. Each slot has separate Ping and speed summaries; fixed failure codes and saturating counters prevent arbitrary data and overflow. Serialize observations for each scanner so delayed writes cannot overwrite newer results. A completed scan with no work is still a successful scan; an individual target's timeout is a monitoring result, not a scanner exception. Lease renewal is independent so a long-running speed test is not mistaken for a stopped Worker.

The administrator-facing health view distinguishes the database connection probe, Hangfire server heartbeat and each scanner's observed state. A live Hangfire server does not prove that Ping or speed scans succeed. Show observation times and distinguish healthy, unhealthy, stale and unknown; missing, expired or implausibly future observations cannot be presented as healthy. Reuse the ASP.NET Core health-check infrastructure and evaluate Microsoft's EF Core health-check package for the SQL probe; preserve the existing liveness endpoint's meaning. A successful database connection does not establish that every operation or migration is healthy.

For receivers, distinguish an implemented Agent endpoint's deployment and database dependency from the most recent **committed** successful reception. No received data is an unknown observation, not a failure or proof of health; rejected and duplicate batches do not establish a newly received batch. The not-yet-implemented OTLP receiver is explicitly not connected, not healthy. Do not claim an end-to-end receiver check when only Web process or database availability was measured.

Acceptance of this foundation requires administrator and negative authorization tests, real SQL migration and bounded-store tests, real job failure and retry with restart, Worker stop/stale/recovery and scanner failure separation, database failure/recovery, real Agent receipt/rejection/duplicate/no-traffic cases, cancellation and deliberate secret-exclusion tests. Failures of the diagnostic backend must remain visible as unavailable and must not be mistaken for a successful write. Other operation sources, future receivers, the full dependency matrix and REQ-39 retention remain separate outstanding acceptance work.
