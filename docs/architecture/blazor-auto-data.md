# Blazor Auto data and identity

REQ-05-T06 establishes a real, minimal protected workspace identity flow. The workspace reports only the current user's name and built-in roles; it does not create sample devices, monitoring data or an artificial production dashboard.

`IWorkspaceIdentityClient` and its DTO live in Contracts. The Web.Client implementation calls the same-origin `/api/v1/workspace/identity` endpoint with the browser's session cookie. The server adapter reads the current `AuthenticationState` and calls the same `WorkspaceIdentityService` used by that endpoint, without looping back over HTTP or forwarding cookies. The service creates a short-lived scope for each read, reloads the account, validates its security stamp and lockout, and reads current roles from Identity. The API enforces the monitoring-read policy and returns no secrets, credentials, EF entities or internal database keys.

The page is prerendered and then becomes interactive. It intentionally repeats this small, read-only authorization check after hydration rather than persisting authenticated identity in serialized component state; this avoids carrying an outdated authorization decision across the handoff. The server circuit and browser do not share a DbContext. Interactive clients recheck every 30 seconds and when the user requests a refresh. A rejected session clears the displayed identity; a failed connection also clears it and displays a retry state rather than presenting stale data as current. Server-side checks remain authoritative immediately on each request or protected operation; the 30-second presentation refresh is not an authorization grace period, and already delivered data cannot be remotely erased from an offline browser.

Interactive Auto initially uses Server when the WebAssembly runtime is not yet cached; the background download does not change an already running component. A later full visit can use WebAssembly after the runtime and required assets are cached. The page uses the same interface and authorization behavior in either mode. `RendererInfo.Name` is exposed only as a non-sensitive HTML data attribute so browser integration tests can distinguish Static, Server and WebAssembly; it is not a monitoring status or a user-facing circuit counter.

Cookie-authenticated API writes still require antiforgery, and third-party bearer credentials remain separate. Do not serialize advanced monitoring data into anonymous HTML or trust an earlier UI role decision when new data is requested. Future resource facades must retain the same server-side authorization and clear or mark stale data on failure.
