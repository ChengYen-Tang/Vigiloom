# API and ingestion contract

REQ-04-T01 defines the common boundary. It is a contract for the relevant future receiver and Agent requirements, not a claim that those endpoints or delivery guarantees are already implemented. ADR-0001, ADR-0002 and ADR-0003 remain authoritative.

## Principals and transport

All authenticated traffic requires TLS, including traffic through a reverse proxy. The deployment must configure trusted proxies explicitly; forwarded headers from arbitrary callers cannot establish HTTPS or a client address. Credentials never appear in URLs, logs, diagnostics, work arguments or ordinary API responses.

There are four distinct principal kinds: a human using an Identity session cookie; a third-party API client; a registered host Agent; and an application/Collector source. A principal in one category is not accepted as another. The server derives identity, authorization and producer identity from the credential and current server-side state, never from a claimed resource ID, address, hostname, `service.name` or batch payload. Revocation and service approval changes are effective at the receiver before accepting the next request, regardless of Agent configuration polling or existing keep-alive connections.

Human browser writes require antiforgery. Third-party API clients use independently issued bearer credentials over TLS and scoped policies; they do not receive human session cookies. Administrative account and credential management remain explicitly restricted to the appropriate human Administrator endpoints unless an endpoint separately defines machine authorization. Agent registration and Agent/source credentials are owned by REQ-18/19 and REQ-22/23 respectively; sharing a transport does not confer another principal's permissions.

For third-party clients, issue a random opaque credential once, store a SHA-256 verifier rather than the secret, and compare verifier bytes in constant time. A 256-bit cryptographically random secret makes a fast hash suitable here; passwords continue to use Identity's password hasher. The credential contains a public UUID v7 identifier and base64url secret and is passed only as `Authorization: Bearer ...`. A credential is independently named, scoped, expirable, rotatable and revocable. Changes are audited without secrets. The verifier is read from the current database state for each request; do not cache acceptance beyond revocation. Rotation issues a new credential without revealing the old one; revoking either credential affects it immediately. UI delivery, lifecycle rules and tests belong to REQ-04-T02.

## Versioned Web API

Routes start with `/api/v1/`. Resource IDs are UUID v7 generated by Vigiloom, serialized as canonical lower-case GUID `D` strings in JSON and responses; input accepts valid `D` strings regardless of case. An ID alone is neither a credential nor a permission. JSON request/response types are explicit DTOs, not EF entities, secrets or SQL `RowId` values. Use UTF-8 and RFC 3339 `DateTimeOffset` timestamps in UTC; query ranges are half-open `[from, to)`, bounded per endpoint, and have a documented maximum. List operations expose bounded pages with a stable ordering and an opaque continuation cursor, or document their existing fixed-size page-number behavior; neither GUID order nor local `RowId` is a timestamp contract.

Missing or invalid credentials produce 401; an authenticated principal without the required scope produces 403; missing or inaccessible resources follow the endpoint's publication policy without leaking private data. Invalid input returns 400, conflicting state 409, expired batches 410, oversized payloads 413, throttling 429 and temporary receiver unavailability 503. Errors use RFC 9457 Problem Details with a stable machine-readable `code`; do not expose credentials, stack traces, SQL, private metadata or raw telemetry. `Retry-After` is supplied for retryable 429/503 responses where known. An HTTP success is not a durable-ingestion acknowledgement unless the receiver explicitly defines it as such.

OpenAPI documents each route's input, output, supported authentication, scopes and status codes. A major version changes a broken contract; additive optional fields preserve old clients. Receivers reject unsupported major versions with 400 and `unsupported_protocol_version` before persistence, rather than interpreting them as a different payload. Per-source and global quotas apply after trustworthy identity is established; unauthenticated traffic has independent coarse limits. Limits apply to decompressed bodies as well as transport bytes.

## First-party Agent batches

The Agent generates each `MessageId` and `BatchId` once using UUID v7, with a fixed `ItemOrdinal` per batch item. It durably queues the exact serialized UTF-8 payload and first-enqueued UTC timestamp before sending, preserving IDs, item order and bytes across retries, restarts and updates. Content hashing uses SHA-256 of the exact payload bytes after HTTP transport decompression; request authentication, received time and other server metadata are not part of the digest. Producer identity comes exclusively from the authenticated, currently authorized Agent.

The shared version-1 batch envelope has `protocolMajor` (integer `1`), `batchId` (GUID string), `firstEnqueuedAt` (UTC timestamp), and `items` (nonempty array). Each item has `messageId` (GUID string), `itemOrdinal` (zero-based integer equal to its array position), `kind` (bounded signal discriminator), `occurredAt` (UTC timestamp, or null when the specific signal permits missing source time) and `data` (the owning signal's DTO). There is no caller-supplied `producerId`. A future Agent receiver defines its route and the registered `kind` DTOs in REQ-19; unknown kinds or invalid IDs, timestamps, ordinals and per-kind fields reject the entire batch. The receiver records its own `receivedAt` separately. Unknown fields are ignored only where the owning compatible version explicitly allows them.

The initial maximum is 1 MiB decompressed or 1,000 items per batch, whichever is reached first. Batches are validated completely before writing and are accepted or rejected as a unit. No partial-success acknowledgement is defined for this first-party path. The recipient coordinates one SQL transaction for the unique `(ProducerId, BatchId)` receipt and every owning module's writes; only a committed transaction permits an acknowledgement. Concurrent duplicate inserts are arbitrated by the SQL unique constraint. Same key and digest returns the original successful result without another insertion; the same key with different bytes returns 409 `batch_conflict` and does not overwrite. A timeout or lost response is ambiguous, so the Agent retries the same batch rather than creating a replacement.

The default maximum resend age is 24 hours from the Agent's persisted first-enqueued time; the receiver rejects expired batches with 410 `batch_expired` and does not silently repack them. Reject timestamps more than five minutes in the future and expose clock problems to the operator. Agent clocks and authenticated producers can be incorrect or malicious: this timestamp check is not a proof of creation time, and the system must report such uncertainty rather than promise permanent exactly-once delivery. The default receipt retention is seven days. Configuration changes must maintain a safe relationship between the permitted resend window, clock/retry grace, all previously accepted configuration generations and receipt retention; never purge a still-acceptable receipt. Document any detected capacity loss or expired queued data as a gap.

The Agent sends every five seconds or when a batch limit is reached; its bounded offline queue defaults to 256 MiB or 24 hours. On disconnection it retains committed queue entries and retries with bounded exponential backoff and jitter. On 429/503 it honors `Retry-After` where provided and preserves the batch. Invalid credentials, revoked registration, version mismatch, conflict, expiration and persistent invalid input require explicit remediation rather than infinite blind retries. A full queue must report loss or backpressure and preserve control data and protected evidence according to the owning feature's documented policy; it must not silently discard accepted data or report it as delivered.

REQ-19 implements the wire format, durable queue, receipt transaction and failure cases. Exact payload schema, retry caps, queue prioritization and per-module ingestion methods belong to that receiver's documented contract; they cannot weaken the guarantees above. REQ-39 owns receipt retention and safe generation transitions.

## Application discovery and standard telemetry

An unapproved application source may populate only the minimum bounded discovery metadata needed for Administrator review; it cannot cause formal telemetry collection, even if it supplies a service ID. The pending view includes unapproved sources seen within the last three minutes and retains actively reporting candidates; approval and revocation are checked centrally. REQ-22 specifies source authentication, limits, expiry and discovery storage before implementing that path.

Standard OTLP and health-check protocols retain their own wire formats, identity, acknowledgement and error semantics. OTLP TraceId and SpanId retain their original byte formats; external instance IDs remain external identifiers. Do not assign first-party batch guarantees to OTLP or infer reliable deduplication from signal content. REQ-23/24 define per-protocol authorization, limits, receiver durability and externally visible status, including any duplicate risk.
