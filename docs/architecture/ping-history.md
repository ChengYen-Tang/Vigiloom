# Ping history and rollup contract

Ping measurements are independent of application health and Agent heartbeat. A raw row keeps its UTC observation and receipt times, original configured target, resolved address when known, monitoring location, outcome and latency. Legacy rows without a target or outcome remain explicitly unidentified; they are never assigned to a current target or a guessed failure category.

Five-minute UTC windows are `[start, end)` and keyed by device, original target (including a distinct legacy null), location and window start. They retain counts per outcome and the sum, minimum and maximum of successful latencies. A timeout, DNS error, permission problem or absent sample is not a zero-millisecond result. Average across windows is weighted by successful sample counts. If a finite legacy value causes a sum to overflow, the window is flagged and its average is unavailable; its counts and finite extrema remain available.

The Ping writer adds each raw row and updates its rollup in the same SQL transaction, after the existing target lease and device checks. The final lease check and transaction commit cover both. A non-null target/generation has the existing unique deduplication constraint. A bounded background job claims older, unaggregated rows, locks each rollup key, marks each raw row as aggregated, and commits each batch atomically. Retries do not count the same row twice. Old observation timestamps, including late measurements, remain in their original window.

The signed-in query accepts one device, one target/location pair and a five-minute-aligned UTC interval of at most seven days. Raw samples are paged by observation time and internal RowId; the RowId is not returned as an external identifier. The chart uses the same selected source and interval and shows missing or all-failed windows as gaps. Until historical backfill finishes, the UI indicates that rollups may be incomplete. A raw sample page may be empty while longer-lived rollups remain available.

REQ-39 owns retention configuration and deletion. Its Ping cleanup must not delete a raw row until its `Aggregated` marker and corresponding rollup are committed, and it must preserve rollups for the configured period. The backfill lock order is raw rows before rollup keys; cleanup must not hold a rollup key while waiting for those raw rows. Concurrent live writes and backfill must not be treated as evidence that arbitrary cleanup is already safe. If a cleanup design removes rollups or adds a late-arrival cutoff, it must specify and test those races and the applicable retention boundary before enabling deletion. This document does not claim that Ping retention or cleanup has already been delivered.

Rollback of the rollup migration refuses to drop nonempty rollups. Operators must preserve or deliberately recover history before a downgrade.
