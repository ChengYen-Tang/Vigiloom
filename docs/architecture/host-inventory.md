# Host inventory contracts

REQ-26 owns collection and authorized queries for operating system, installed software, accounts, and installed updates. REQ-31 owns their presentation. Inventory is evidence from specific sources, not proof that all software or available security updates are known.

## Collection and source coverage

- A registered Agent collects at startup and, by default, every six hours. Collection uses the existing shared cooperative sampling budget. It never sends passwords, password hashes, private keys, or tokens.
- The adjustable inventory interval is an independently versioned capability setting, with built-in, platform and device layers. It uses the existing Agent settings synchronization and ownership mechanisms; changing transport or metric revisions is not a substitute for tracking the inventory policy. Changing the interval affects the next new pass, never the identity or content of a generation already queued. Saved configuration, the policy actually applied by the worker and a successful inventory pass are separate states. An Agent or central version without the inventory setting reports its application state as unknown. The allowed interval is 15 minutes to 7 days, with six hours as the built-in default.
- Native package stores can change while read; a completed read describes the source's observed enumeration, not an atomic point-in-time operating system snapshot. Detect available source change indicators and report partial when they change during enumeration; rescan rather than infer removals from a detected inconsistent read.
- Report OS and process architecture separately. On 64-bit Windows read both machine uninstall registry views explicitly, including from an x86 Agent; report scope and access failures. On 32-bit Windows use only its available view. Registry view alone is not proof of a package's executable architecture. Uninstall registry data excludes unregistered applications and other users' per-user installations.
- Linux dpkg and RPM databases are distinct sources; RPM retains concurrently installed versions, and dpkg reports installed packages including held packages. Package-maintainer and RPM-vendor fields retain their respective source meanings and do not claim to identify the original software publisher. Local account and group files cover local entries, not NSS or directory-service accounts; group-file members must be combined with each account's primary GID when presenting membership. Missing tools, unsupported distributions, inaccessible sources, failures, and partial scans are distinguishable from a complete empty result. Installed package versions and Windows KBs are not a claim that all available updates are installed or that the host is vulnerability-free.
- Windows accounts and groups use the local machine SAM through Microsoft's account-management API. Direct group member SIDs use paged NetLocalGroupGetMembers level 0 without resolving domain accounts; a group may include domain principals or nested groups. Membership lookup failures mark the source partial. Calls into the OS directory provider are synchronous and cancellation is observed between results, not while a provider call is in flight; an active paged membership enumeration is drained before cancellation returns.
- Runtime-reported processor count is the logical CPU allowance observed at process startup, not the number of physical cores or a live quota measurement. Linux runtime OS version describes the kernel/platform; distribution name and version need their own source.
- The host record reports the Agent informational release version (including prerelease), physical memory reported by the operating system, and OS boot time. Linux boot time comes from `/proc/stat` and distribution ID/version from `os-release`; a missing optional VERSION_ID remains unknown. Windows boot time comes from the operating-system WMI provider. A failed required read marks this source partial so it cannot replace the last complete host record. These values describe OS-visible resources and may differ from container or physical-host limits.
- Network inventory consists of separate OS-visible interface and unicast-IP entries; address records reference their interface and are not used as device identity. Volume inventory reuses the existing bounded local-volume collector: it reports supported local mount points and capacities, excludes remote or unrecognized mounts, and does not claim a one-to-one physical disk mapping. Virtual interfaces and loopback can be present. Per-source reads can be partial when an interface or eligible mount cannot be inspected.
- Windows quick-fix records use the WMI `Win32_QuickFixEngineering` CBS view. It does not enumerate every update mechanism or pending updates. The source's localized installation-date text is retained as text rather than guessed as an exact UTC time; the observation time is recorded separately. The WMI timeout limits each enumeration wait, not total provider execution, and cancellation is observed between waits rather than interrupting an in-flight COM call.
- Preserve source-native identifiers, ecosystem, full version, architecture where known, and observed UTC time. User and group inventory never contains authentication secrets. Stable device ownership comes from the authenticated Agent, not a hostname or an address in the payload.

## Snapshots and reliable transport

- One source produces a full snapshot with a durable generation, source identity, observation time, completeness and bounded chunks. Chunk contents, message IDs, batch IDs and serialized bytes remain unchanged on retries; chunks obey the existing Agent batch limits and owner checks.
- Persist generation and queued chunks durably before advertising a completed scan. Queue exhaustion, cancellation, source access failure, or incomplete scans do not replace the last complete snapshot and cannot imply that missing items were removed.
- The receiver authenticates the Agent and commits each batch and receipt atomically. A new snapshot becomes current only after all chunks are present and verified for the same source and generation. Out-of-order, duplicate, conflicting and delayed chunks must not overwrite a later committed generation. Generations are allocated durably per Agent and source rather than inferred from UUID ordering or the Agent's clock.
- A generation has an immutable manifest: authenticated Agent, source and scope, format version, expected chunk count, total records and bytes, and content digest. A unique `(Agent, source, generation, ordinal)` identifies each chunk; a conflicting manifest or content is rejected. A complete empty snapshot has an explicit manifest and empty chunk, rather than no messages.
- Schema 4 measures each chunk as the UTF-8 JSON bytes of its `items` array using the fixed schema-4 serialization options. `TotalBytes` is the sum of those array lengths. Each chunk digest is SHA-256 over those bytes; the manifest digest is SHA-256 over the 32-byte chunk digests concatenated in chunk-index order. Sender and receiver must preserve the schema-4 fields and serialization rules, verify exact item totals, byte totals, unique source keys and manifest equality, and only then publish.
- A snapshot is limited to 100,000 group-member entries in total, in addition to the per-group and serialized-byte limits. Exceeding this bound is an observable failed collection, never a complete empty or truncated snapshot.
- Incomplete staging has a bounded lifetime. Expiry records a terminal, observable generation outcome; late chunks cannot recreate it or change the current snapshot. An authenticated Agent polls the central outcome for its outstanding source generation after restart and while waiting for completion; it does not rely on the last chunk's response alone. On expired or irrecoverably rejected generations, it records the failure and schedules a fresh full scan under a new generation. Outcome records remain available until the Agent can observe them or a documented longer recovery horizon has elapsed; exceeding that horizon must itself cause a fresh scan, not a presumed success. An acknowledged chunk's receipt still gives the original acknowledgement on retry; receipt replay never resurrects expired staging. No data is marked removed merely because staging expired.
- Incomplete staging expires 24 hours after the first chunk, using the database clock. A Worker job expires at most 100 generations every five minutes, skips busy Agents while continuing through candidates, and rechecks each under its Agent transaction lock.
- Retain a durable closed-generation high-water mark per Agent and source even after outcome details and staged chunks expire. Advance it atomically with each terminal outcome; no previously closed generation can be opened again. A newer generation fences older incomplete generations rather than permitting late publication. This fence is distinct from the receipt replay window and is removed only with the identity lifecycle that makes the old Agent unable to authenticate.
- Retain at most one current complete payload per source and one active staging generation per Agent. Before replacing a complete snapshot, derive its changes; do not keep unbounded full historical payloads. As an initial safety ceiling, reserve at most 32 MiB of canonical item arrays across all current sources and at most 32 MiB for the one active replacement. Before accepting its first chunk, calculate the projected current total after replacement; a snapshot that cannot fit is permanently rejected with a visible capacity reason, not endlessly retried. Contention for an otherwise admissible active slot is retryable. Keep the old current snapshot until replacement completes. At 500 Agents this bounds canonical item-array bytes to 31.25 GiB, excluding JSON envelopes, indexes, receipts, change history and SQL overhead; it is not a capacity or throughput guarantee. Bounded change history and retention remain subject to REQ-39.
- A single per-Agent inventory producer lease serializes source scans. All chunks of one generation are enqueued contiguously in one durable queue transaction; a full queue advances neither generation completion nor source state. On restart, the producer resumes the outstanding generation and checks its central outcome before scheduling another. This prevents a later source's first chunk from blocking an earlier source's remaining chunks in the FIFO sender. Invalid or interleaved clients remain bounded by the staging expiry and must receive an observable terminal outcome.
- The central receiver, expiry worker, quota reservation and publication use the same per-Agent transaction lock. Where authentication is needed, lock order is device/Agent authorization, replay policy, then inventory Agent lock; maintenance that needs authorization follows the same order. This serializes the shared budget across sources and avoids a separate per-source quota race.
- Generations belong to an Agent identity and source scope. Credential rotation that preserves AgentId preserves the sequence; re-enrollment with a new AgentId creates a separate sequence, fenced by the current device registration before publication. Scope or parser changes create a distinct source generation and never compare a new identity's counter to an old identity's counter. Keep historical attribution. Bound chunk counts, bytes, incomplete staging lifetime and retained snapshots; do not clean data in a way that breaks receipt replay guarantees. Report collection and delivery failures without logging sensitive inventory content.
- Before reserving a generation the Agent obtains, from the authenticated central platform, the highest generation seen for that Agent and source, including an active generation. The new durable local reservation exceeds both that value and its local counter. A missing or rolled-back local database therefore cannot silently reuse an old generation. If central state cannot be authenticated, defer a new snapshot; do not assume its high-water mark is zero.
- Enqueueing schema-4 inventory atomically marks the local transport database format as version 4, which older senders reject before touching its batches. After all inventory batches are acknowledged or explicitly removed, and no inventory generation is outstanding, the queue restores its prior compatible format (version 2 or 3 depending on whether the log schema exists). Rejected inventory remains retained for diagnosis and keeps the version-4 fence. An updater still needs to detect this fence and explain or defer an incompatible downgrade; changing the marker alone does not implement the update workflow.
- Complete empty snapshots are distinct from failed or incomplete scans. Current snapshot metadata records the last attempt, last complete observation and collection status. The API derives changes between complete snapshots using source-specific identity; strings retain source case and must not silently collide under database collation.

## Access and verification

- Only authenticated Administrator and Read only users may query inventory. Agent credentials cannot query arbitrary devices; anonymous projection contains no inventory data.
- The private inventory API returns each source's last attempt separately from its current complete snapshot. Snapshot chunks are pinned to the returned SnapshotId; if a replacement becomes current, subsequent requests for the old snapshot return 404 and the caller must reload the source view. Change history uses a bounded UTC range and an opaque descending cursor; concurrent writes can appear on a fresh query, so a cursor traversal is not a database-wide point-in-time snapshot.
- Change records retain both the Agent's observation time and the SQL Server publication time. REQ-39 owns retention policy and cleanup; it can use the indexed publication time rather than trusting the Agent's clock. Cleanup must preserve each source's current and active snapshots, its latest terminal outcome and its closed-generation fence, so delayed recovery cannot be mistaken for success or reopen an old generation.
- Verify source completeness and missing privileges, x86/x64 registry views, empty versus failed scans, removal and reinstallation, chunk order and duplication, queue backpressure, restart and re-enrollment, and non-regression on stale generations. Validate schema, indexes, atomicity and replay using real SQL Server; validate target OS collection on supported operating systems before declaring it supported.
- REQ-31 supplies the actual user-facing inventory views and cross-requirement acceptance. REQ-26 remains In progress until that acceptance is complete.
