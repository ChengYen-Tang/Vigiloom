# Agent update handoff

REQ-20 uses an independent, privileged Updater and a lower-privilege Agent. The local IPC and recovery worker are implemented; the installer and central package endpoints remain required for end-to-end operation.

The Agent's existing machine secret stays in its user-scoped vault. After verifying the local Updater's identity, the Agent may hand the Updater the current update ID and credential over an OS-protected local connection. The credential is held only in memory for that attempt, never in command-line arguments, environment variables, logs or the recovery journal. The Updater uses its protected installation configuration for the central URL, expected device identity, trust roots and installation paths. It authenticates the machine against the central identity endpoint, obtains the current assignment itself, and verifies the publisher manifest and package. A local message cannot supply an executable path, URL, installation arguments or an assertion that a package is already trusted.

Before stopping the Agent and again before switching, the Updater checks the current central assignment and manifest validity. A connection failure cannot authorize a switch. Once an update is accepted, the Agent stopping and its IPC connection closing must not cancel the Updater's transaction. On Updater restart, recovery uses the local journal without the credential or central connectivity; the restored Agent can later initiate another attempt. Recovery and updates must run through one local coordinator and exclusive ownership of the installation.

The installer establishes and verifies the following OS boundaries:

- **Windows:** a local named pipe with an explicit ACL for the Agent service SID and the Updater identity, with first-instance protection. Before sending a credential, the Agent checks the pipe server process against the Service Control Manager's Updater process. `CurrentUserOnly` is insufficient for services with different identities.
- **Linux:** a Unix-domain socket in a root-owned directory that the Agent cannot modify; the socket permits the dedicated Agent group to connect. Both peers verify the other endpoint's OS credentials. The Agent cannot replace the socket or its parent directory.

The installer also fixes the two service identities and keeps the Agent state, credential vault and durable queue outside version directories. The Updater's installation, trust and staging directories are not writable by the Agent. If an archive comes from an Agent-writable location, the Updater must first copy it into its own protected directory and verify the copied bytes before use.

The Updater reads installer-protected `Vigiloom:Updater` settings: `InstallationRoot`, `StateDirectory`, `Server`, and `DeviceId`. Windows additionally needs `AgentSid`; Linux needs `IpcDirectory`, `AgentUid`, and `AgentGroupId`. The authenticated TUF store lives under `StateDirectory/trust` and the package cache under `StateDirectory/cache`. The installer must provision the trust root and protect these paths before enabling handoff; missing settings leave handoff inactive. `InstallationRoot/updater.lock` is held while recovering and processing requests, so two updater processes cannot control the same installation at once.

For first installation, the setup process can run `Vigiloom.Updater provision-trust <absolute-root-file> <sha256-fingerprint>` with `Vigiloom__Updater__StateDirectory` set to the protected updater state directory. The root and fingerprint must be obtained independently from a trusted distribution; the command verifies the fingerprint and will not overwrite an existing trust store. This command does not install or start either service.

The installer writes the one-time enrollment value to `enrollment.pending` in the Agent's private state directory before starting its service. It must contain exactly the 84 ASCII characters, without a BOM or newline. On Linux the file is owned by the Agent account and mode 0600, with its state directory mode 0700. On Windows the protected state directory is owned by the Agent identity and grants access only to it, SYSTEM and Administrators. The Agent registers under its own identity, retries temporary failures, and removes the bootstrap file after its identity is saved. Installation must preserve an existing identity and must not replace a pending enrollment while the service is running.

See Microsoft's [named pipe security](https://learn.microsoft.com/windows/win32/ipc/named-pipe-security-and-access-rights), [pipe server process identification](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), and the Linux [Unix-domain socket](https://man7.org/linux/man-pages/man7/unix.7.html) documentation. The need to separate package acquisition, authenticated content and the updater lifecycle is also reflected in the open-source [Wazuh agent upgrade design](https://github.com/wazuh/wazuh/blob/main/docs/ref/modules/agent_upgrade/README.md).
