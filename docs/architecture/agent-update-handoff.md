# Agent update handoff

REQ-20 uses an independent, privileged Updater and a lower-privilege Agent. The installer, central package endpoints and local IPC support installation and administrator-selected updates.

The Agent's existing machine secret stays in its user-scoped vault. After verifying the local Updater's identity, the Agent may hand the Updater the current update ID and credential over an OS-protected local connection. The Updater validates and stores the credential in its protected state directory so it can poll for assignments when the Agent is unavailable; it is not put in command-line arguments, environment variables, logs or the recovery journal. The Updater uses its protected installation configuration for the central URL, expected device identity, and installation paths. It authenticates the machine against the central identity endpoint, obtains the current assignment itself, and verifies the assigned manifest and package hashes. A local message cannot supply an executable path, URL, installation arguments or an assertion that a package is already trusted.

Before stopping the Agent and again before switching, the Updater checks the current central assignment and package integrity. A connection failure cannot authorize a switch. Once an update is accepted, the Agent stopping and its IPC connection closing must not cancel the Updater's transaction. On Updater restart, an interrupted operation is recorded as failed without automatically changing the selected Agent version. The administrator can inspect the failure and select an available package to roll back; the Updater itself is not downgraded with the Agent. Recovery and updates run through one local coordinator and exclusive ownership of the installation.

The installer establishes and verifies the following OS boundaries:

- **Windows:** a local named pipe with an explicit ACL for the Agent service SID and the Updater identity, with first-instance protection. Before sending a credential, the Agent checks the pipe server process against the Service Control Manager's Updater process. `CurrentUserOnly` is insufficient for services with different identities.
- **Linux:** a Unix-domain socket in a root-owned directory that the Agent cannot modify; the socket permits the dedicated Agent group to connect. Both peers verify the other endpoint's OS credentials. The Agent cannot replace the socket or its parent directory.

The installer also fixes the two service identities and keeps the Agent state, credential vault and durable queue outside version directories. The Updater's installation and staging directories are not writable by the Agent. If an archive comes from an Agent-writable location, the Updater must first copy it into its own protected directory and verify the copied bytes before use.

The Updater reads installer-protected `Vigiloom:Updater` settings: `InstallationRoot`, `StateDirectory`, `Server`, and `DeviceId`. Windows additionally needs `AgentSid`; Linux needs `IpcDirectory`, `AgentUid`, and `AgentGroupId`. The package cache lives under `StateDirectory/cache`. The installer must protect the installation and state paths; missing or invalid required settings stop the Updater host. `InstallationRoot/updater.lock` is held while recovering and processing requests, so two updater processes cannot control the same installation at once.


The installer writes the one-time enrollment value to `enrollment.pending` in the Agent's private state directory before starting its service. It must contain exactly the 84 ASCII characters, without a BOM or newline. On Linux the file is owned by the Agent account and mode 0600, with its state directory mode 0700. On Windows the protected state directory is owned by the Agent identity and grants access only to it, SYSTEM and Administrators. The Agent registers under its own identity, retries temporary failures, and removes the bootstrap file after its identity is saved. Installation must preserve an existing identity and must not replace a pending enrollment while the service is running.

The Windows bundle determines x86 or x64 from the Agent and Updater executables and rejects mixed architectures. Windows Server 2012 and 2012 R2 require Extended Security Updates under the .NET 10 support policy. On 2026-11-17, a self-contained x86 test bundle was installed on Windows 11 Enterprise x64 build 26100 in Windows Sandbox: both services started under their intended accounts, Agent stop/start left the Updater running, and both services restarted after a guest reboot with pending enrollment unchanged. Networking was disabled and the enrollment was synthetic; this does not validate real registration, update, removal, or a 32-bit operating system.

Windows setup registers the Agent and Updater Application event sources while elevated, so the low-privilege Agent can write diagnostics. A separate offline Windows Sandbox test confirmed an encrypted pending identity could be read after recreating the Agent service under the same virtual account, and that a failed installation removed event sources it had just created. This does not establish preservation of an already registered identity or queued batches through uninstall and reinstall.

See Microsoft's [named pipe security](https://learn.microsoft.com/windows/win32/ipc/named-pipe-security-and-access-rights), [pipe server process identification](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), and the Linux [Unix-domain socket](https://man7.org/linux/man-pages/man7/unix.7.html) documentation. The need to separate package acquisition, authenticated content and the updater lifecycle is also reflected in the open-source [Wazuh agent upgrade design](https://github.com/wazuh/wazuh/blob/main/docs/ref/modules/agent_upgrade/README.md).
