# Agent configuration: REQ-19 implementation contract

This is a work-in-progress implementation contract, not a claim that REQ-19 or its UI has been delivered. The current transport scheduling slice applies heartbeat, settings polling and sender intervals; collector settings, queue lifecycle and the complete acceptance remain outstanding. The overall scope and precedence are fixed by ADR-0003 and REQ-19.

## Effective values and revisions

- Resolve each field from built-in default, platform setting and then an explicit device override. A reset removes the override; group membership and public templates do not change configuration. An override belongs to the device, not to the current machine credential, so rotating a credential does not erase the setting.
- An Administrator changes the platform or device setting through the authorized UI and API. Validate the complete resulting settings before committing; record actor and server time, reject stale concurrent edits, and do not store credentials in settings or audit details. Read only can see non-secret monitoring and effective values, but cannot modify settings or enter administrator-only management routes.
- Derive stable effective revisions from versioned canonical representations of the resolved fields for each independently applied capability group. Any effective change must change the relevant revision, including changes to platform values inherited by an individual device. A revision is an opaque configuration version, not a resource identifier or a SQL row ordering key. A conditional Agent request may return 304 only for a group whose exact revision is already durably applied by that Agent.
- Assemble each response from a consistent read of the platform and device layers; concurrent updates must not produce a mixture that was never committed. An authenticated Agent may read only its own device's configuration. Recheck the current machine credential, device binding and eligible status at the authorization boundary; revocation must not wait for a polling interval.

## Agent lifecycle

- On startup and then every five minutes with ±20% jitter, fetch the effective settings using the current registered HTTPS identity. Allow cancellation, bound the response and its read time, and use the existing factory-managed client without redirect or cookie forwarding. Retry failures on later polls without blocking heartbeat or batch delivery.
- The wire representation has an explicit schema version, required fields, capability-group revisions and no secrets. Validate the schema, value ranges, cross-field relationships and revision before changing any effective value in a group. An unsupported or invalid group leaves that group's last successfully applied values intact and records an explicit failure; it is never reported as applied. Other valid independent groups can still apply. Central desired values and per-group applied revisions/status remain distinct: an overall success is shown only when every requested field is actually applied, while unsupported capabilities are visible per field. Do not send unimplemented collector fields as part of a supposedly fully applied transport group.
- Persist each last successfully applied group atomically in the protected Agent state directory, bound to the Agent identity and server. Recover it at restart, including when offline. Publish the new in-memory snapshot only after durable replacement succeeds. A response can be saved only if a local write-generation token still equals the token observed before that request; compare-and-swap occurs under the cross-process identity lease. Generate a fresh token for every successful write, even if values revert to a previously used revision, so an older response cannot replace a newer group after an A→B→A transition. On conflict, do not publish the stale response; reload the saved group and reconcile before reporting applied status. On first start without a valid snapshot, use the safe built-in values without pretending a remote revision was applied. Never hold the identity lease while waiting on HTTP.
- Heartbeat and batch workers consume effective values rather than independent copies of defaults. A timer change takes effect without requiring an Agent restart; a currently running operation finishes or cancels under its existing policy. Sender backoff and explicit Retry-After remain authoritative. Collection settings for capabilities not implemented by this Agent must be reported as unsupported or pending, not silently described as active.
- Send desired/applied revisions, last successful application time and bounded, non-secret failure information through an ordered authenticated report. The central UI distinguishes pending, applied, failed and offline and shows the time of the last report. A stale report or a restored server must not make old data appear current. Heartbeat connectivity remains independent of queue health and of the device's Ping state.
- Heartbeat interval transitions require a central safety envelope: **before** handing out a longer interval, durably widen the Agent's effective offline threshold to cover that interval. Retain the maximum threshold for all delivered, potentially still applicable settings, even if an administrator subsequently changes the desired value again or a report is lost. The current implementation widens this envelope but deliberately does not shrink it; after an interval decrease, the UI therefore continues to show the conservative threshold and offline detection can be delayed. The initial 30-second interval uses a 90-second threshold. A future decrease must not be implemented solely by acknowledging the latest delivery: a copied identity can have another process with an independent local lock and an older response in flight. Shrink only when the protocol fences or expires every older delivery and execution, including duplicate identities, and prove this across lost confirmations, reordered deliveries, administrator changes and offline transitions.

## Safety and compatibility

- Do not treat an Agent-supplied timestamp as proof of batch creation time. A shorter offline replay window or inbox retention must not be applied until the server can preserve the guarantees of the previous generation, account for in-flight retries and clock skew, and validate the retention relationship. Configuration must not enable the still-unimplemented inbox cleanup or silently discard an existing queue.
- A reduced queue capacity causes backpressure for new data; it does not silently remove existing batches. The queue's configured limit is logical payload capacity, not a promise about SQLite file size. Preserve quarantined data and its diagnostic status. Any actual loss must eventually be counted and visible, rather than inferred from a full queue.
- Protocol and local-format changes must tolerate a rolling central/Agent upgrade. Unknown future local formats must not be overwritten, and an older central platform must not cause the Agent to erase its last valid configuration. A successful configuration download is not proof that each separate OS capability or collector supports the requested value.
- REQ-40 owns recovery from central database restore; it must fence old report sessions before receiving traffic and provide a safe way for affected Agents to resume. REQ-20 must check local configuration and queue format compatibility before upgrades or downgrades. Neither integration is complete solely because this contract exists.

## Required evidence

Use MSTest with isolated LocalDB for actual SQL migrations, concurrent edits, layer resolution, credential revocation and cleanup. Exercise HTTP authentication and conditional responses; run a real Agent host against the receiver to verify startup polling, jitter bounds, live worker changes, offline restart, invalid or unsupported updates, stale concurrent responses, atomic-file failure, retry, and accurate per-group applied/error status. Validate both Windows and Ubuntu CI. UI journeys require Product Design and must cover Administrator and Read only, inherited values, override reset, pending/offline/failed states and safe handling of retention changes.

The .NET configuration/options APIs provide typed binding and validation, but do not themselves provide authenticated per-device distribution, atomic last-good persistence, or applied-status reporting. Reuse framework HTTP, JSON and options primitives and the existing identity store; do not introduce another configuration service merely for these operations. See [Microsoft .NET configuration](https://learn.microsoft.com/dotnet/core/extensions/configuration) and [options validation](https://learn.microsoft.com/dotnet/core/extensions/options-validation-generator).
